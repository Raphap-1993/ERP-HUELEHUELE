# Fase 1 - Scoring Y Automatizaciones Comerciales

## Objetivo

Homologar scoring determinista y automatizaciones comerciales simples sobre
`customer_relationship_case`, formalizando tier visible, razon corta,
triggers fuente, eventos derivados, catalogo cerrado de reglas y side effects
auditables sin abrir journeys, `commercial_opportunity` ni IA opaca.

## Problema de negocio que resuelve este slice

Huele Huele necesita priorizar mejor la relacion comercial activa del cliente
sin depender solo de lectura manual del pipeline y del timeline. El gap no es
abrir otra entidad comercial, sino derivar una lectura confiable de calor
comercial y disparar acciones simples, trazables y seguras sobre el mismo
caso para que `marketing` opere reglas y `ventas` consuma sus efectos en
`/crm`.

## Flujo funcional consolidado

### 1. Calculo y lectura del score comercial

1. Un trigger fuente impacta el `customer_relationship_case`.
2. El sistema recalcula el score de forma determinista y auditable.
3. El puntaje interno se colapsa a `cold`, `warm` o `hot`.
4. Si cambia el resultado efectivo, el slice deriva `score_changed`.
5. `/crm` muestra solo el tier visible y una razon corta del score.

### 2. Evaluacion de reglas y acciones simples

1. Una regla activa recibe un trigger valido.
2. El sistema procesa reglas por `order` determinista.
3. Cada regla evalua filtros simples de elegibilidad sobre el mismo caso.
4. La regla ejecuta solo acciones del catalogo cerrado del slice.
5. Todo efecto permitido queda trazado sobre el `customer_relationship_case`.

### 3. Idempotencia, cooldown y side effects seguros

1. Antes de ejecutar un side effect, el sistema evalua deduplicacion base.
2. Si la combinacion `ruleId + customerRelationshipCaseId + actionType`
   sigue activa, no repite el efecto.
3. Cada regla puede bloquear repeticion adicional usando su propio
   `cooldown`.
4. El score puede recalcularse aunque una tarea o campaign quede bloqueada.
5. Ninguna automatizacion cambia `pipelineStage` ni `status`.

## Requerimientos funcionales

### RF-01. El slice vive sobre el mismo caso transversal del cliente

- `012` extiende el mismo `customer_relationship_case`
- no crea un agregado nuevo
- sigue existiendo un solo caso por cliente canonico
- el slice no abre `commercial_opportunity`

### RF-02. Score determinista, auditable y sin override manual

- el score se calcula por reglas explicitas y reproducibles
- el score no admite override manual en este corte
- cada recalculo debe poder explicarse con trazabilidad del trigger y la
  razon visible resultante
- el slice no incorpora heuristicas opacas ni IA para puntuar

### RF-03. Tier visible y puntaje interno separado

- la UI solo muestra `scoreTier`
- `scoreTier` usa `cold`, `warm` y `hot`
- el puntaje interno existe solo como mecanismo de calculo
- el puntaje interno no se muestra en `/crm`
- el caso expone una razon visible corta para explicar el tier

### RF-04. Triggers fuente canonicos del slice

- el slice usa `pipeline_stage_changed`
- el slice usa `followup_due`
- el slice usa `followup_overdue`
- el slice usa `order_confirmed`
- el slice usa `payment_confirmed`
- el slice usa `case_reopened`

### RF-05. Eventos derivados simples del slice

- el slice deriva `score_changed` cuando cambia el resultado efectivo del
  score
- el slice deriva `followup_candidate_detected` cuando la regla detecta que
  el caso requiere accion comercial adicional
- el slice no abre un event engine mas amplio en este corte

### RF-06. Catalogo cerrado de reglas simples

- cada regla se define en un catalogo predefinido
- cada regla expone `active` o `inactive`
- cada regla expone `order` de evaluacion determinista
- cada regla expone `cooldown`
- cada regla declara un trigger, filtros simples y una accion
- el slice no abre builder libre de reglas

### RF-07. Filtros simples de elegibilidad

- las reglas pueden filtrar por dimensiones operativas simples del mismo caso
- el set minimo soportado puede incluir `commercialChannel`, `pipelineStage`,
  `scoreTier` y `status`
- los filtros no abren joins complejos ni subpipelines nuevos

### RF-08. Catalogo cerrado de acciones permitidas

- `recalculate_score`
- `suggest_priority`
- `create_followup_task`
- `enqueue_existing_campaign`

Reglas:

- `suggest_priority` no cambia `priority` automaticamente
- `create_followup_task` opera sobre el mismo caso transversal
- `enqueue_existing_campaign` solo reutiliza campaigns existentes del slice
  `006`
- `followup_candidate_detected` es evento derivado, no accion del catalogo

### RF-09. Idempotencia y cooldown por regla

- la deduplicacion base usa `ruleId + customerRelationshipCaseId + actionType`
- el mismo side effect no debe duplicarse para la misma regla y el mismo caso
- cada regla puede definir su propia ventana `cooldown`
- la deduplicacion y el `cooldown` deben dejar trazabilidad del bloqueo
- el bloqueo de side effects no impide recalcular score cuando toca

### RF-10. Guardrails de automatizacion comercial simple

- las automatizaciones no cambian `pipelineStage`
- las automatizaciones no cambian `status`
- las automatizaciones no alteran `commercialOwner` ni `assignee`
- el slice no abre un ciclo comercial nuevo fuera del caso existente
- el slice mantiene todos los efectos dentro de `/crm` o en la frontera ya
  existente de `006`

### RF-11. Superficie visible y ownership operativo

- `/crm` es la superficie visible principal del slice
- `marketing` gobierna el catalogo y la activacion de reglas
- `ventas` consume score, razon visible, sugerencias y tareas dentro de `/crm`
- no se abre una consola separada para operar automatizaciones simples

## Requerimientos no funcionales

- trazabilidad completa de triggers, reglas evaluadas, eventos derivados y
  side effects
- consistencia entre `006`, `010`, `011` y el mismo
  `customer_relationship_case`
- reproducibilidad del score y del orden de reglas
- seguridad operativa para evitar tareas o campaigns duplicadas
- lectura rapida del tier y de su razon visible sin exponer el puntaje interno
