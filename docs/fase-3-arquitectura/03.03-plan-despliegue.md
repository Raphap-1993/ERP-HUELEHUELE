# 03.03 Plan De Despliegue

Fecha de corte: 2026-05-26.

## Objetivo

Definir como desplegar el slice `checkout publico + pago manual + payment gateway idempotente` sin alterar la topologia vigente ni comprometer la operacion productiva.

## Principios De Release

1. LOCAL sigue siendo la fuente de verdad del codigo.
2. La BD productiva no se reemplaza con datos locales.
3. El runtime productivo sigue corriendo en los mismos cuatro procesos PM2.
4. `manual payment` debe seguir operativo aunque el provider online se deshabilite.
5. Cualquier automatizacion futura del provider entra apagada y se habilita solo tras smoke checks.

## Topologia Productiva Sin Cambios

| Dominio o acceso | Proceso | Puerto | Cambio por este slice |
| --- | --- | --- | --- |
| `https://huelegood.com` | `huelegood-web` | `3000` | no |
| `https://admin.huelegood.com` | `huelegood-admin` | `3005` | no |
| `https://api.huelegood.com` | `huelegood-api` | `4000` | si, nuevas rutas internas del gateway |
| sin dominio publico | `huelegood-worker` | n/a | no para MVP, posible soporte a retries futuros |

No se crea un proceso `payments-gateway`. La frontera canonica vive dentro de `huelegood-api`.

## Variables De Entorno Del Slice

Se reusan `OPENPAY_*` y se agregan flags canonicos:

| Variable | Uso | Valor sugerido inicial |
| --- | --- | --- |
| `PAYMENT_ONLINE_PROVIDER_ACTIVE` | provider online activo | `openpay` o `none` |
| `PAYMENT_ONLINE_AUTO_CONFIRM_ENABLED` | habilita confirmacion automatica por webhook | `false` |
| `PAYMENT_ONLINE_CAPTURE_STATUSES` | lista de estados externos que cierran venta | `captured,paid` |
| `OPENPAY_WEBHOOK_SECRET` | validacion de firma del webhook | secreto productivo |
| `HUELEGOOD_ENABLE_ASYNC_MANUAL_REVIEW` | cola manual existente | mantener valor vigente |

Regla: si falta configuracion online critica, el sistema debe degradar a manual visible, no fallar abierto.

## Secuencia De Despliegue Recomendada

### Fase A. Preparacion

1. validar `npm run typecheck`
2. validar `npm run test:erp-sales`
3. validar `npm run build`
4. revisar que `shared/.env.production` tenga flags y secretos nuevos
5. si hay cambio de schema para tablas `payment_gateway_*`, ejecutar backup productivo antes del release

### Fase B. Release brownfield seguro

1. crear release timestamp como en `docs/infra/deployment-strategy.md`
2. desplegar API, web y admin en el release nuevo
3. recargar PM2 con `--update-env`
4. mantener `PAYMENT_ONLINE_AUTO_CONFIRM_ENABLED=false`
5. mantener `PAYMENT_ONLINE_PROVIDER_ACTIVE=openpay` solo si el provider ya fue validado; si no, arrancar con `none`

### Fase C. Smoke checks obligatorios

#### API y salud

- `https://api.huelegood.com/api/v1/health/liveness`
- `https://api.huelegood.com/api/v1/health/readiness`
- `https://api.huelegood.com/api/v1/health/operational`

#### Storefront

- abrir `/checkout`
- confirmar que `manual payment` sigue visible
- si `PAYMENT_ONLINE_PROVIDER_ACTIVE=openpay`, confirmar que existe una sola opcion online visible
- crear checkout manual y verificar que el pedido queda en revision

#### Backoffice

- abrir `/pagos` y verificar que la bandeja sigue orientada a comprobantes manuales
- abrir `/pedidos` y verificar que la accion de conciliacion online sigue en `Pedidos > Operacion`
- confirmar que el copy no mezcla rutas manuales y online

#### Provider online

- crear un checkout online sandbox
- verificar `providerReference` y `checkoutUrl`
- confirmar que el pedido queda `pending_payment`
- confirmar que no se auto-confirma mientras `PAYMENT_ONLINE_AUTO_CONFIRM_ENABLED=false`

## Estrategia De Habilitacion

| Paso | Flag | Expectativa |
| --- | --- | --- |
| 1 | `PAYMENT_ONLINE_PROVIDER_ACTIVE=none` | solo manual visible y estable |
| 2 | `PAYMENT_ONLINE_PROVIDER_ACTIVE=openpay` | manual + una opcion online activa |
| 3 | `PAYMENT_ONLINE_AUTO_CONFIRM_ENABLED=false` | conciliacion online sigue manual desde `Pedidos > Operacion` |
| 4 | `PAYMENT_ONLINE_AUTO_CONFIRM_ENABLED=true` | solo tras validar webhook, firma e idempotencia |

La fase 4 no debe activarse en el mismo release que introduce la frontera si todavia no existe evidencia de webhook idempotente en preproduccion o sandbox.

## Migraciones Y Datos

Si la implementacion agrega tablas `payment_gateway_attempts` y `payment_gateway_events`:

- ejecutar backup antes de `prisma:push` o migracion equivalente;
- no tocar seeds productivos;
- verificar que las nuevas tablas no bloqueen el flujo manual si quedan vacias;
- confirmar indices unicos para idempotencia antes de habilitar webhooks.

## Rollback

### Rollback rapido de comportamiento

1. cambiar `PAYMENT_ONLINE_PROVIDER_ACTIVE=none`
2. mantener `PAYMENT_ONLINE_AUTO_CONFIRM_ENABLED=false`
3. recargar `huelegood-api` y `huelegood-web`

Resultado esperado: el checkout vuelve a manual visible como unica ruta publica sin perder pedidos previos.

### Rollback de codigo

1. apuntar `current` al release anterior
2. recargar PM2 con `--update-env`
3. correr smoke checks de salud, `/checkout`, `/pagos` y `/pedidos`

### Rollback de datos

- solo con backup productivo;
- no usar datos locales;
- no revertir manualmente eventos ya confirmados sin auditoria.

## Riesgos De Despliegue

| Riesgo | Control |
| --- | --- |
| el provider online queda mal configurado y rompe el checkout | degradacion a `manual` con `PAYMENT_ONLINE_PROVIDER_ACTIVE=none` |
| webhook duplicado confirma dos veces | indice unico en `payment_gateway_events` y comando idempotente en `orders` |
| copy operativo confunde al equipo | smoke checks funcionales en `/pagos` y `/pedidos` antes de cerrar release |
| schema nuevo impacta produccion | backup previo y activacion de flags despues del despliegue |

## Cierre Esperado

Un release correcto de este slice deja:

- mismo footprint de infraestructura;
- `manual payment` estable y visible;
- cero ambiguedad operativa entre `Pagos` y `Pedidos > Operacion`;
- provider online encapsulado detras de flags, no quemado en la UX ni en el despliegue.
