# 05.00 Mapeo De Implementacion: Checkout y Payments

## Objetivo

Dejar documentado como el codigo vigente resuelve hoy el slice `checkout publico + pago manual + frontera futura de gateway`, sin vender como terminado lo que todavia depende de conciliacion manual en backoffice.

## Estado Vigente Del Slice

- El checkout publico vive en `apps/web/components/checkout-workspace.tsx`.
- La UI actual inicializa `paymentMethod` en `manual` y no expone un selector visible para alternar a `openpay`.
- El cliente web mantiene ambos contratos HTTP en `apps/web/lib/api.ts`: `createManualCheckout()` y `createOpenpayCheckout()`.
- La API publica ambas rutas en `apps/api/src/modules/commerce/commerce.controller.ts`: `POST /store/checkout/manual` y `POST /store/checkout/openpay`.
- `Pagos` resuelve solicitudes manuales con comprobante.
- `Pedidos > Operacion` es la vista canonica para trazabilidad comercial, registro manual directo y conciliacion online.
- No existe webhook productivo ni confirmacion automatica de gateway como cierre canonico de este corte.

## Comportamiento Implementado Hoy

### 1. Checkout publico

- Cotiza via `POST /store/checkout/quote`.
- Busca cliente previo por documento y, si no existe coincidencia local para `DNI`, consulta `ApiPeru`.
- Captura direccion con ubigeo normalizado.
- Para provincias fuerza `carrier=shalom`, `agencyName` y `payOnPickup=true`.
- Sube el comprobante via `POST /store/checkout/evidence`.

### 2. Pago manual desde web

- `CommerceService.createManualCheckout()` crea el pedido y la solicitud manual en una sola operacion.
- El pedido entra a revision, no a confirmacion automatica.
- La evidencia queda enlazada al pedido y a la `manualRequest`.
- La aprobacion posterior confirma inventario y deja `commercialTrace.route = manual_request`.

### 3. Revision manual en backoffice

- `Pagos` consume `GET /admin/payments` y `GET /admin/payments/manual-requests`.
- Aprobar usa `POST /admin/payments/manual-requests/:id/approve`.
- Rechazar usa `POST /admin/payments/manual-requests/:id/reject`.
- La aprobacion registra actor, nota, referencia, evidencia y evento de auditoria.
- El rechazo cancela el pedido y libera inventario comprometido.

### 4. Frontera actual de gateway

- `CommerceService.createOpenpayCheckout()` ya crea pedido web con `providerReference=OP-*`.
- `confirmOnlinePayment()` existe y esta conectado al detalle de `Pedidos > Operacion`.
- La suite de dominio valida que una orden `openpay` no pueda entrar por `registerAdminManualPayment()`.
- Lo que hoy falta no es el contrato basico, sino el cierre autonomo del proveedor.

## Guardrails Reales Del Corte

- `Pagos` no confirma `openpay` pendiente; esa cola es solo de comprobantes manuales.
- `Pedidos > Operacion` no debe usar `register manual` sobre pedidos `openpay`.
- La misma orden online no debe descontar stock dos veces.
- La evidencia del comprobante no se trata como URL publica abierta de negocio.
- La UI publica actual no reabre cupones ni `vendorCode`, aunque la API conserva soporte tecnico.

## Frontera Futura Del Gateway

Capacidad ya sembrada:

- endpoint `POST /store/checkout/openpay`
- `providerReference` online
- `checkoutUrl`
- `confirmOnlinePayment()` desde admin
- enum `openpay_provider` reservada en contratos

Capacidad no cerrada en esta capa inicial:

- selector publico de `openpay` en el checkout vigente
- webhook o callback productivo que confirme solo con estado del proveedor
- conciliacion automatica por `captured/paid`
- outbox o bandeja persistente dedicada para eventos de gateway

Mientras eso no cambie, el modelo canonico sigue siendo: checkout publico con pago manual expuesto, y conciliacion online solo como frontera operativa controlada desde backoffice.
