# 03.01 Decisiones De Tecnologia

Fecha de corte: 2026-05-26.

## Objetivo

Fijar las decisiones tecnicas del slice `checkout publico + pago manual + payment gateway idempotente` sin abrir un rediseño total del monorepo.

## Resumen Ejecutivo

La estrategia es incremental y brownfield:

- no se crean microservicios ni procesos PM2 nuevos;
- se conserva el checkout publico actual en Next.js;
- se introduce una frontera interna `payment-gateway` dentro de la API NestJS;
- se mantiene `payments` como modulo manual;
- se refuerza la idempotencia con persistencia propia para proveedor online.

## Decisiones Canonicas

### TD-01. Mantener monolito modular en cuatro procesos

**Decision**

Se conserva `web`, `admin`, `api` y `worker` como procesos unicos del sistema.

**Razon**

La topologia vigente ya coincide con `docs/architecture/overview.md`, `docs/infra/deployment-strategy.md` y `docs/infra/pm2-services.md`. Crear un servicio nuevo solo para pagos online sube complejidad operacional sin resolver el problema principal, que hoy es de ownership e idempotencia.

**Impacto**

- sin cambios en PM2;
- sin cambios en Nginx mas alla de una ruta webhook futura al mismo `huelegood-api`;
- toda la trazabilidad sigue compartiendo PostgreSQL, Redis, auditoria y observabilidad actuales.

### TD-02. Introducir un modulo interno `payment-gateway`

**Decision**

Se incorpora un modulo NestJS dedicado a provider online activo, sesiones de cobro, firma, webhooks, normalizacion de estados externos e idempotencia por evento.

**Razon**

Hoy `commerce.service.ts` y `orders.service.ts` contienen conocimiento directo de Openpay. Esa mezcla dificulta soportar un provider activo unico pero intercambiable.

**Impacto**

Rutas candidatas:

- `apps/api/src/modules/payment-gateway/payment-gateway.module.ts`
- `apps/api/src/modules/payment-gateway/payment-gateway.service.ts`
- `apps/api/src/modules/payment-gateway/payment-gateway.controller.ts`
- `apps/api/src/modules/payment-gateway/providers/openpay/openpay.provider.ts`
- `apps/api/src/modules/payment-gateway/providers/openpay/openpay.mapper.ts`

### TD-03. Un solo provider online activo

**Decision**

El runtime debe resolver un solo provider online activo a la vez. Para este corte homologado el runtime queda en `PAYMENT_ONLINE_PROVIDER_ACTIVE=none`; `openpay` se conserva solo como primer provider contemplado por la frontera futura.

**Razon**

La operacion actual y la UX publica no necesitan orquestacion multi-provider. Multiplicar proveedores ahora complejiza soporte, copy, conciliacion y QA sin un caso real validado.

**Impacto**

- configuracion canonica por env: `PAYMENT_ONLINE_PROVIDER_ACTIVE=openpay|none`;
- el checkout publico nunca lista dos opciones online simultaneas;
- si el provider activo es `none`, el checkout solo expone `manual`;
- si en el futuro el provider activo pasa a `openpay`, la UI publica puede exponer `manual + una opcion online`.

### TD-04. Mantener `manual` visible como ruta base del checkout

**Decision**

`manual payment` sigue siendo la ruta base del checkout. Hoy queda como unica ruta visible; si en el futuro se habilita un provider online real, `manual` permanece como fallback coexistente.

**Razon**

La operacion vigente ya soporta comprobantes manuales, y el negocio necesita una salida estable ante degradacion del provider o validaciones fuera de linea.

**Impacto**

- `apps/web/components/checkout-workspace.tsx` no puede ocultar manual;
- `apps/api/src/modules/commerce/commerce.service.ts` mantiene el circuito de evidencia y revision;
- el despliegue puede fallar cerrado a manual sin romper el checkout.

### TD-05. Idempotencia en dos niveles y con persistencia

**Decision**

Se combinan dos estrategias:

- checkout idempotente por `clientRequestId + requestHash`;
- eventos/provider callbacks idempotentes por `provider + providerEventId` o `provider + providerReference + normalizedStatus`.

**Razon**

El mapa actual en memoria de `orders.service.ts` sirve para el flujo local, pero no alcanza para retries externos ni para webhooks.

**Impacto**

Artefactos a introducir:

- `payment_gateway_attempts`
- `payment_gateway_events`

Y tipos compartidos minimos nuevos en `packages/shared`.

### TD-06. Confirmacion automatica futura solo en `captured` o `paid`

**Decision**

El gateway solo puede disparar confirmacion automatica cuando el evento normalizado sea `captured` o `paid`.

**Razon**

`authorized` no garantiza liquidacion final ni cierre comercial seguro. El pedido no debe quedar confirmado ni mover stock definitivo por un estado intermedio.

**Impacto**

- se requiere un mapper explicito de estados externos a internos;
- la automatizacion futura convivira con conciliacion manual mientras `PAYMENT_ONLINE_AUTO_CONFIRM_ENABLED=false`;
- `orders` recibira un comando ya normalizado, no el payload crudo del proveedor.

### TD-07. `payments` sigue siendo modulo manual, no gateway online

**Decision**

No se amplia `payments` para que sea tambien duenio de proveedor online.

**Razon**

`payments` ya concentra comprobantes manuales, colas de revision y bandeja `Pagos`. Mezclarle provider SDK, firma y webhooks volveria a acoplar manual y online en una sola pieza.

**Impacto**

- `payments.service.ts` se mantiene enfocado en solicitudes manuales;
- `payments-workspace.tsx` conserva copy excluyente para comprobantes;
- la conciliacion online visible sigue en `orders-workspace.tsx`.

### TD-08. Compatibilidad brownfield de endpoints

**Decision**

El corte inicial puede mantener `POST /store/checkout/openpay` como alias de compatibilidad, pero el contrato preferido pasa a ser provider-neutral.

**Razon**

Evita romper el checkout actual mientras se introduce la frontera canonica.

**Impacto**

Estrategia recomendada:

- nuevo endpoint canonico: `POST /api/v1/store/checkout/online`;
- wrapper legacy: `POST /api/v1/store/checkout/openpay` delega internamente al gateway activo;
- `apps/web/lib/api.ts` migra a `createOnlineCheckout()` y deja `createOpenpayCheckout()` como adaptador transitorio.

### TD-09. BullMQ solo para manual review y retries diferidos

**Decision**

La creacion del checkout online sigue siendo sincrona. BullMQ se usa para:

- aprobacion/rechazo manual;
- reintentos operativos diferidos;
- notificaciones;
- replays controlados de eventos si hiciera falta.

**Razon**

El cliente necesita respuesta inmediata con `checkoutUrl` o con estado de revision manual.

**Impacto**

- `apps/worker/src/main.ts` puede sumar procesamiento de replay de gateway en el futuro;
- no se mete la apertura de checkout del proveedor en la cola.

### TD-10. Evidencia manual privada y reuse de `media`

**Decision**

La evidencia manual sigue subiendo via `mediaService` y debe mantenerse no publica por defecto.

**Razon**

Ya existe una ruta de upload en `commerce.controller.ts`; conviene endurecer su politica antes que crear un subsistema paralelo.

**Impacto**

- la spec tecnica debe revisar URLs abiertas de evidencia;
- cualquier refactor debe preservar auditabilidad y retencion operativa.

## Decisiones Explicitamente Rechazadas

| Decision rechazada | Motivo |
| --- | --- |
| dos providers online activos simultaneos | complica UX y operacion sin valor real en este corte |
| confirmar por `authorized` | riesgo comercial e inventario prematuro |
| mover conciliacion online a `Pagos` | rompe la regla de `Pedidos > Operacion` como vista canonica del pedido |
| integrar SDK del proveedor directamente en `web` | expone coupling y debilita control del backend |
| crear un microservicio de pagos | sobrecosto operacional para un problema interno de modulo |

## Resultado Tecnologico Esperado

Al terminar la implementacion de esta SDD el sistema debe tener:

- una frontera online intercambiable sin romper el checkout publico;
- roles modulares consistentes entre `commerce`, `orders`, `payments` y `payment-gateway`;
- persistencia minima para idempotencia externa;
- capacidad de mantener `manual` como fallback visible aunque el provider online se deshabilite.
