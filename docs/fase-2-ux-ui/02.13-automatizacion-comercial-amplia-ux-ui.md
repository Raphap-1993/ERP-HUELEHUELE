# Fase 2 - Automatizacion Comercial Amplia UX/UI

## Objetivo

Formalizar la UX operativa del slice `014-automatizacion-comercial-amplia`
como una capa de journeys comerciales multi-step dentro de `/crm`, anclada
al mismo detalle del cliente y a la misma logica comercial ya homologada,
sin abrir una consola nueva ni vender un workflow builder libre.

## Superficies

### Superficie principal

- detalle del cliente dentro de `/crm`
- sigue mostrando el resumen general del caso comercial
- si existe oportunidad activa, la mantiene como contexto ligado
- suma un bloque especifico de journeys
- el bloque de journeys no reemplaza el bloque del caso ni el del deal

### Superficie secundaria

- bandeja de journeys dentro de `/crm`
- muestra por defecto instancias `active` y `paused`
- permite filtrar `completed` y `cancelled`
- no abre ruta aparte ni dashboard paralelo

## Contrato UX visible minimo

- el detalle del cliente debe distinguir claramente:
  - caso comercial general
  - oportunidad activa ligada cuando exista
  - instancia(s) de journey
- cada journey visible expone:
  - template de origen
  - estado `active`, `paused`, `completed` o `cancelled`
  - `journeyAssignee`
  - ultimo paso o hito
  - razon de pausa o cancelacion cuando aplique
  - referencia a oportunidad activa si el template la usa
- los pasos `manual_review` deben resolverse dentro del mismo `/crm`
- la UI debe poder leer la traza del journey sin salir a otra consola

## Elementos visibles clave

- resumen de instancia activa o pausada
- badge de estado del journey
- template name o etiqueta del journey
- `journeyAssignee`
- milestone trail
- ultimo paso ejecutado
- paso manual pendiente cuando exista
- razon de pausa o cancelacion
- referencia contextual a oportunidad activa
- bandeja secundaria de journeys por cliente o por filtro operativo

## Lecturas secundarias o derivadas

- si no hay journeys activos, el detalle puede mostrar estado vacio o accion
  de lanzamiento manual excepcional
- un caso puede tener varios journeys activos si son de templates distintos
- un mismo template no puede duplicarse sobre un caso mientras siga no
  terminal
- la resolucion de pasos manuales debe sentirse como trabajo comercial
  operativo, no como mantenimiento tecnico del engine
- el journey puede encolar una campana existente o sugerir prioridad, pero la
  UI no debe vender mutaciones automaticas del pipeline o del deal

## Guardrails UX

- el slice vive dentro de `/crm`; no abre consola separada
- la UI no debe sugerir builder libre de journeys
- la UI no debe sugerir chaining entre journeys
- la UI no debe mezclar estado del caso, del deal y del journey como si
  fueran una sola state machine
- la UI no debe prometer inbox ni mensajeria bidireccional real
- `manual_review` bloquea la continuidad del journey hasta su resolucion

## Regla UX critica

- el usuario debe entender que sigue operando el mismo cliente canonico
  dentro de `/crm`, pero ahora con una capa de secuencias multi-step, waits y
  pasos humanos que orquestan el trabajo comercial sin reemplazar el caso ni
  el deal puntual

## Criterio de cierre

- `014` queda documentado como capa de automation comercial amplia dentro del
  mismo `/crm`
- el detalle del cliente y la bandeja secundaria de journeys quedan
  defendidos como las unicas superficies necesarias del corte
- la separacion entre caso, deal y journey queda explicita sin abrir una app
  nueva
