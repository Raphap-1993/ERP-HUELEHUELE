# Fase 1 - CRM Manual Ampliado

## Objetivo

Homologar el seguimiento manual ampliado sobre pedidos ya elegibles dentro
de `orders`, formalizando `order_follow_up_case`, timeline manual,
`assignee`, `nextStep`, `followUpAt` y tareas opcionales sin convertir el
slice en CRM por cliente ni mezclarlo con campaigns, fulfillment o
notifications.

## Estado actual que se conserva

- `Pedidos > Operacion` ya es la superficie visible principal del seguimiento
  operativo del pedido
- `crmStage` y `commercialTrace` ya quedaron canonizados en el slice `008`
- `Ventas` ya aparece como owner natural del seguimiento del pedido
- `Marketing` ya tiene acceso secundario a dominios comerciales y CRM
- el runtime actual todavia no canoniza un CRM manual estructurado por
  pedido, pero si deja el hueco natural para extender `orders`
- el slice debe vivir dentro de `orders`, no en `customers`

## Problema de negocio que resuelve este slice

Huele Huele necesita una capa manual seria para operar seguimientos humanos
sobre pedidos ya elegibles: saber quien lleva el caso, que sigue, cuando
toca volver a actuar y que evidencia manual queda registrada, sin convertir
el tab operativo del pedido en un CRM general por cliente ni mezclarlo con
campaigns, fulfillment o dashboards.

## Flujo funcional consolidado

### 1. Apertura y asignacion del caso manual

1. El pedido ya tiene `crmStage` relevante.
2. `ventas` abre el caso manual explicitamente.
3. El caso registra `assignee`, `nextStep` y `followUpAt`.
4. El pedido queda con un solo `order_follow_up_case`.
5. La vista operativa deja visible quien sigue el pedido y que toca hacer.

### 2. Seguimiento manual del pedido

1. El caso ya existe y sigue abierto.
2. `ventas` o `marketing` agregan entradas manuales al timeline.
3. Cada entrada usa un `type` canonico y una `note` libre.
4. El caso puede tener tareas opcionales con `pending` y `done`.
5. Mientras siga abierto, `nextStep` y `followUpAt` permanecen obligatorios.

### 3. Cierre, cancelacion y reapertura

1. `ventas` puede mover el caso a `resolved` o `waiting_customer`.
2. Todo cambio de estado deja una entrada `status_change`.
3. Si el pedido llega a `Delivered` o `Completed`, el caso se resuelve
   automaticamente.
4. Si el pedido cae o falla comercialmente, el caso se cancela
   automaticamente.
5. Si el pedido sigue elegible, `ventas` puede reabrirlo exigiendo otra vez
   `nextStep` y `followUpAt`.

## Requerimientos funcionales

### RF-01. `orders` es el agregado principal

- la unidad operativa principal del slice es el pedido
- `order_follow_up_case` vive dentro de `orders`
- el slice no abre un CRM transversal por cliente

### RF-02. Un solo caso por pedido

- solo puede existir un `order_follow_up_case` por pedido
- el caso solo se abre sobre pedidos con `crmStage` relevante
- el slice no permite multi-caso historico por pedido en este corte

### RF-03. Ownership operativo explicito

- `ventas` es owner operativo principal del slice
- `marketing` tiene acceso operativo secundario
- `admin` y `super_admin` actuan como override

### RF-04. Estados canonicos del caso

- el caso usa `open`
- el caso usa `waiting_customer`
- el caso usa `resolved`
- el caso usa `cancelled`

### RF-05. `nextStep` y `followUpAt` como disciplina minima

- `nextStep` y `followUpAt` son obligatorios mientras el caso este en
  `open` o `waiting_customer`
- esos campos pueden vaciarse cuando el caso quede `resolved` o
  `cancelled`
- la reapertura vuelve a exigir ambos campos

### RF-06. Timeline manual estructurado

- el timeline manual admite `note`, `call`, `whatsapp`, `email` y
  `status_change`
- cada entrada guarda actor, fecha, `type`, `note` y referencia o evidencia
  opcional
- las entradas del timeline son inmutables una vez creadas

### RF-07. Tareas opcionales editables

- las tareas del caso son opcionales
- cada tarea usa `title`, `status` y `dueDate`
- las tareas usan `pending` y `done`
- las tareas si se pueden editar o marcar como completadas

### RF-08. Cierre automatico por lifecycle del pedido

- `Delivered` y `Completed` resuelven automaticamente el caso
- si el pedido cae o falla comercialmente, el caso se cancela
  automaticamente
- el cierre automatico no borra el timeline previo

### RF-09. Superficie visible del slice

- `Pedidos > Operacion` es la superficie visible principal
- la bandeja secundaria vive dentro del mismo modulo de `Pedidos`
- la bandeja muestra por defecto `open` y `waiting_customer`

## Requerimientos no funcionales

- trazabilidad de actor, nota, referencia y cambios de estado del caso
- consistencia entre elegibilidad del pedido y apertura del caso
- claridad de ownership entre `ventas`, `marketing` y `orders`
- disciplina operativa minima con `nextStep` y `followUpAt`
- exclusion explicita de CRM por cliente, mensajeria real y dashboards
