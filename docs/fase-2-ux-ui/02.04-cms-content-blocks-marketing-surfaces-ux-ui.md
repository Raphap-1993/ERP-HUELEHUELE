# Fase 2 - UX/UI CMS Content Blocks Marketing Surfaces

## Objetivo

Formalizar la UX del CMS editorial vigente de Huele Huele sin convertir
`/admin/cms` en un page builder libre ni reabrir el rediseño visual del
storefront.

## Fuentes de runtime

- `apps/admin/components/cms-workspace.tsx`
- `apps/admin/lib/api.ts`
- `apps/api/src/modules/cms/admin-cms.controller.ts`
- `apps/api/src/modules/cms/cms.service.ts`
- `apps/web/features/storefront-v2/lib/content.ts`
- `apps/web/features/storefront-v2-premium/layouts/storefront-v2-premium-page.tsx`
- `docs/storefront-v2-premium-landing.md`

## Mapa de vocabulario y snapshot

- `site settings` en lenguaje operativo = `siteSetting` en
  `CmsSnapshotResponse`
- `hero copy` en lenguaje operativo = `heroCopy` en `CmsSnapshotResponse`
- `navigation` en lenguaje operativo = `webNavigation` en
  `CmsSnapshotResponse`
- este slice usa esos tres nombres de negocio y runtime como el mismo contrato
  singleton global, no como conceptos separados

## Contrato actual de media publica

- el snapshot CMS no tiene un objeto top-level `media`
- la media publica vigente viaja hoy dentro de `siteSetting`
- los campos publicos actuales son `headerLogoUrl`, `adminSidebarLogoUrl`,
  `heroProductImageUrl`, `loadingImageUrl` y `faviconUrl`
- los uploads de `/admin/cms/site-settings/*` actualizan esos campos y el
  snapshot los devuelve nuevamente dentro de `siteSetting`
- `media` se documenta aqui como capacidad operativa de soporte, no como una
  segunda estructura de snapshot paralela

## Superficies

### `/admin/cms`

- es la superficie operativa principal del slice
- carga un snapshot editorial unico desde `GET /admin/cms`
- resume paginas, banners, FAQs y navegacion con metricas de lectura rapida
- el editor de pagina trabaja por `slug` conocido, estado
  `draft/published/archived`, `seoMeta` por ruta y bloques JSON
- `banners`, `faqs` y `testimonials` se operan como colecciones cortas con
  `active/inactive`
- las tablas de SEO y navegacion funcionan como lectura de salida del snapshot,
  no como constructor visual
- el dominio CMS tambien expone endpoints dedicados para `site settings`,
  `hero copy` y `navigation`, mas uploads de media que hoy actualizan
  `siteSetting`; este slice los trata como singleton globales aunque el
  workbench actual priorice pagina, SEO y colecciones editoriales

### Storefront y rutas publicas conocidas

- la home publica consume atomos CMS concretos, no una composicion libre de
  pagina completa
- `loadStorefrontV2Content()` usa `heroCopy`, `featuredProductSlugs`,
  `banners`, `faqs` y `testimonials` `active`, con fallback a defaults
  editoriales cuando el snapshot falla
- `StorefrontV2PremiumExperience` consume `heroCopy`,
  `siteSetting.heroProductImageUrl`, `faqs` y `testimonials` `active`; la
  media publica visible sigue entrando por `siteSetting` y la narrativa visual
  premium sigue curada en codigo
- `catalogo`, `mayoristas`, `trabaja-con-nosotros`, `cuenta` y `checkout`
  siguen siendo rutas conocidas del dominio CMS, no slugs arbitrarios creados
  desde admin
- `cuenta` y `checkout` pueden operar con `robots` `noindex,nofollow`
- la web publica debe sentirse como contenido editorial actualizable, no como
  un site builder gobernado desde marketing

## Bloques conocidos por ruta

- `home`: `hero`, `promo-banner`, `featured-products`, `benefits`, `faq`
- `catalogo`: `hero`, `product-grid`
- `mayoristas`: `hero`, `wholesale-plans`, `lead-form`
- `trabaja-con-nosotros`: `hero`, `vendor-application-form`
- `cuenta`: `auth`, `loyalty`
- `checkout`: `checkout-summary`, `payment-methods`
- `promo-banner` en `home` consume `banners` `active`
- `faq` en `home` consume `faqs` `active`
- `testimonials` se consumen hoy desde la coleccion top-level del snapshot y
  no desde un bloque canonico de `pages.blocks`

## Contrato UX del slice

- `marketing` publica contenido real sobre rutas conocidas sin depender de
  deploy ni de aprobacion multinivel
- `site settings`/`siteSetting`, `hero copy`/`heroCopy` y
  `navigation`/`webNavigation` se leen como el mismo set de singleton globales
  del sitio
- el CMS administra `seoMeta` por ruta y bloques compatibles por superficie
  conocida
- la media publica visible del slice vive hoy dentro de `siteSetting`, no en
  un objeto adicional del snapshot
- la publicacion directa no implica libertad para crear nuevas rutas ni nuevas
  familias visuales desde admin
- el storefront solo renderiza activos publicables y conserva fallback seguro
  si el snapshot no es usable

## Regla UX critica

- `/admin/cms` debe leerse como workbench editorial operativo, no como
  constructor visual libre
- el `slug` de pagina sigue atado al mapa conocido del producto
- la UX publica no debe prometer que cada bloque JSON tenga representacion
  visual inmediata en todas las superficies; el render sigue sujeto al contrato
  por ruta y al consumo real del storefront
- este slice no mezcla campaigns, segments, CRM ampliado ni art direction
  premium como alcance funcional del CMS

## Criterio de cierre

- `/admin/cms` queda nombrado como superficie operativa principal del slice
- los singleton globales, las rutas conocidas y los bloques tipados quedan
  descritos sin inventar un page builder nuevo
- el consumo publico y el fallback seguro quedan documentados sin contradecir
  el runtime vigente
