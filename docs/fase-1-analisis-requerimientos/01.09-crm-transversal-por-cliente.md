# Fase 1 - CRM Transversal Por Cliente

## Objetivo

Homologar el workbench comercial transversal sobre cliente canonico dentro
de `/crm`, formalizando `customer_relationship_case`,
`commercialOwner`, `assignee`, `nextStep`, `followUpAt`, timeline
transversal, tareas opcionales, clasificacion comercial y origen canonico
sin contaminar `007` ni absorber `009`.

## Estado actual que se conserva

- `/crm` ya es la superficie visible natural del detalle de cliente
- `007` ya fija el cliente canonico, el merge y los conflictos de identidad
- `009` ya fija el seguimiento manual ampliado por pedido
- `Ventas` ya aparece como owner natural del frente comercial de clientes
- `Marketing` ya tiene acceso secundario al modulo de CRM
- el runtime actual todavia no canoniza un workbench comercial transversal
  sobre cliente, pero si deja el hueco natural dentro de `/crm`
- el slice debe vivir sobre `customers`, no sobre `orders`

## Problema de negocio que resuelve este slice

Huele Huele necesita una capa seria para operar la relacion comercial activa
con un cliente como cuenta: saber quien es su owner comercial, cual es el
siguiente movimiento, cuando toca retomarlo y como leer pedidos o seguimientos
previos sin duplicar toda la historia transaccional ni mezclar identidad,
campaigns o pipeline comercial amplio.

## Flujo funcional consolidado

### 1. Apertura y clasificacion del caso transversal

1. El cliente entra a trabajo comercial activo.
2. `ventas` o `marketing` abren el caso transversal explicitamente.
3. El caso registra `commercialOwner`, `assignee`, `classification`,
   `origin`, `nextStep` y `followUpAt`.
4. El cliente queda con un solo `customer_relationship_case`.
5. El detalle de `/crm` deja visible quien lleva la relacion y que sigue.

### 2. Timeline y workbench del cliente

1. El caso ya existe y sigue activo.
2. `ventas` o `marketing` agregan entradas manuales al timeline.
3. El timeline tambien muestra `order_reference` y
   `follow_up_reference` automaticos.
4. El resumen comercial mantiene `commercialOwner`, `assignee`,
   `nextStep` y `followUpAt`.
5. El caso puede tener tareas opcionales con `pending` y `done`.

### 3. Merge, cierre y reapertura

1. `ventas` puede mover el caso a `resolved` o `dormant`.
2. Todo cambio de estado deja una entrada `status_change`.
3. Si el caso se reabre, vuelve a exigir `nextStep` y `followUpAt`.
4. Si `007` fusiona clientes, el caso se reancla al cliente canonico destino.
5. No pueden quedar dos casos activos para el mismo cliente canonico.

## Requerimientos funcionales

### RF-01. `customers` es el dominio ancla

- la unidad operativa principal del slice es el cliente canonico
- `customer_relationship_case` vive sobre el cliente canonico
- el slice no reemplaza el maestro de identidad de `007`

### RF-02. Un solo caso por cliente canonico

- solo puede existir un `customer_relationship_case` por cliente canonico
- el caso existe solo cuando hay trabajo comercial activo
- el cliente puede tener caso aunque todavia no tenga pedidos

### RF-03. Ownership operativo explicito

- `ventas` es owner operativo principal del slice
- `marketing` tiene acceso operativo secundario
- `admin` y `super_admin` actuan como override

### RF-04. Estados canonicos del caso

- el caso usa `open`
- el caso usa `waiting_customer`
- el caso usa `dormant`
- el caso usa `resolved`

### RF-05. `nextStep` y `followUpAt` como disciplina minima

- `nextStep` y `followUpAt` son obligatorios mientras el caso este en
  `open` o `waiting_customer`
- esos campos pueden vaciarse cuando el caso quede `dormant` o
  `resolved`
- la reapertura vuelve a exigir ambos campos

### RF-06. Timeline transversal estructurado

- el timeline admite `note`, `call`, `whatsapp`, `email`,
  `status_change`, `order_reference` y `follow_up_reference`
- cada entrada manual guarda actor, fecha, `type`, `note` y referencia o
  evidencia opcional
- las entradas del timeline son inmutables una vez creadas

### RF-07. Referencias automaticas read-only

- `order_reference` y `follow_up_reference` aparecen automaticamente
- las referencias no se editan manualmente desde el caso transversal
- el timeline no duplica toda la historia transaccional del cliente

### RF-08. Tareas opcionales editables

- las tareas del caso son opcionales
- cada tarea usa `title`, `status` y `dueDate`
- las tareas usan `pending` y `done`
- las tareas si se pueden editar o marcar como completadas

### RF-09. Clasificacion comercial manual

- la clasificacion comercial vive en este slice y no en `007`
- el caso usa `prospect`, `active`, `inactive` y `key_account`
- la clasificacion es manual en este corte

### RF-10. Origen canonico del caso

- el caso usa `manual_outreach`
- el caso usa `post_sale_followup`
- el caso usa `reactivation`
- el caso usa `service_issue`

### RF-11. Superficie visible del slice

- el detalle del cliente en `/crm` es la superficie visible principal
- la bandeja secundaria vive dentro del mismo modulo `/crm`
- la bandeja muestra por defecto `open` y `waiting_customer`

## Requerimientos no funcionales

- trazabilidad de actor, nota, referencia y cambios de estado del caso
- consistencia entre cliente canonico, merge y caso transversal
- claridad de ownership entre `ventas`, `marketing` y `customers`
- disciplina operativa minima con `nextStep` y `followUpAt`
- exclusion explicita de campaigns, scoring, pipeline amplio y mensajeria
  real
