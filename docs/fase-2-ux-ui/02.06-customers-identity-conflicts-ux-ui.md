# Fase 2 - Customers Identity Conflicts UX/UI

## Objetivo

Formalizar la UX operativa vigente de `/crm` como workbench de clientes y
conflictos de identidad, sin convertir este slice en CRM comercial amplio ni
en una superficie de seguimiento de pedidos.

## Fuentes de runtime

- `apps/admin/app/crm/page.tsx`
- `apps/admin/components/crm-workspace.tsx`
- `apps/admin/lib/api.ts`
- `apps/api/src/modules/customers/customers.controller.ts`
- `apps/api/src/modules/customers/customers.service.ts`
- `apps/api/src/modules/orders/orders.service.ts`

## Superficies

### `/crm`

- es la superficie operativa principal del slice
- abre con metricas de clientes, activos, con pedidos, conflictos y opt-in
- ofrece una CTA unica `+ Nuevo cliente`
- muestra tabla de conflictos de identidad con pedido, cliente detectado,
  senales, candidatos y accion `Resolver`
- muestra tabla de clientes cuya columna principal visible es `Cliente`
  (`customer.fullName`), seguida por `Contacto`, `Estado`, `Pedidos`,
  `Direccion` y `Acciones`
- resuelve carga y error con mensajes inline simples
- no muestra pipeline comercial, timeline transversal ni acciones de campaign

### Dialogo `Detalle del cliente`

- muestra perfil, direcciones y pedidos recientes vinculados operativamente
- expone email, telefono, estado y total de pedidos
- muestra documento, opt-in y ultimo pedido
- lista direcciones persistidas y marca la principal
- lista pedidos recientes como contexto de lectura
- no expone `crmStage` ni acciones comerciales del pedido

### Formulario `Nuevo cliente` / `Editar cliente`

- captura `firstName`, `lastName`, `email`, `phone`, `password`,
  `documentType`, `documentNumber`, `marketingOptIn`, `status` y direccion
- exige nombre, apellido y email
- exige password temporal al crear
- trata la direccion como bloque opcional, pero si se inicia exige campos
  minimos de direccion
- no expone campos de pipeline comercial ni notas de seguimiento

### Resolucion de conflictos y merge

- el dialogo de conflicto permite `assign_existing`, `merge` e `ignore`
- el dialogo de conflicto muestra senales y candidatos disponibles
- el dialogo de merge permite seleccionar cliente destino y notas
- la UI presenta la fusion como regularizacion operativa, no como borrado de
  historia

## Contrato UX del slice

- `customers` es el agregado visible principal del workbench
- la experiencia prioriza higiene de identidad y correccion del perfil vivo
- los pedidos recientes se usan como contexto, no como ownership funcional
- `deleteCustomer` aparece como accion disponible, pero la UX no lo presenta
  como camino principal del modulo
- el slice no promete `crmStage`, seguimiento comercial, campaigns, wholesale
  ni loyalty

## Regla UX critica

- `/crm` debe sentirse como workbench operativo de clientes y conflictos
- la pantalla debe dejar claro que corrige identidad viva sin reescribir el
  pasado transaccional de `orders`
- merge y resolucion deben leerse como decisiones operativas auditable, no
  como limpieza destructiva del historial

## Criterio de cierre

- `/crm` queda documentado como superficie principal visible del slice
- metricas, clientes, conflictos, detalle y merge quedan nombrados sin
  redisenar el runtime
- la ausencia de `crmStage` y de seguimiento comercial en la pantalla queda
  explicitada sin sobreprometer un CRM ampliado
