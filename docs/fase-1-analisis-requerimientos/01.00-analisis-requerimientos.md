# Fase 1 - Analisis de Requerimientos

## Objetivo

Instanciar el slice inicial `checkout publico + pago manual con comprobante + conciliacion operativa manual + frontera futura de payment gateway idempotente` sobre la documentacion homologada, sin alterar el estado operativo vigente.

## Alcance del slice

### Dentro de alcance

- checkout publico en `/checkout`
- wizard de tres pasos para pedido, datos/envio y pago/confirmacion
- pago manual visible con billetera virtual y carga de comprobante
- revision operativa humana del comprobante
- confirmacion manual controlada del pedido desde backoffice
- trazabilidad de pedido, pago, evidencia, actor y referencia
- separacion operativa entre `Pagos` y `Pedidos > Operacion`
- frontera futura de un payment gateway online con interfaz idempotente

### Fuera de alcance

- reemplazar el flujo publico vigente por un gateway online visible hoy
- activar confirmacion automatica productiva por webhook
- reabrir cupones o codigos de vendedor en la UI publica
- redisenar `Pagos` o `Pedidos > Operacion` mas alla de sus responsabilidades canonicamente documentadas
- resolver en esta fase los hallazgos de inventario, reserva temprana o balance negativo detectados en la auditoria E2E

## Estado actual que se conserva

- el checkout publico visible hoy cierra con pago manual; no expone una pasarela online activa
- la API mantiene soporte tecnico para `Openpay`, `couponCode` y `vendorCode`, pero esa superficie no se reactiva en este corte
- la confirmacion comercial oficial sigue siendo manual y controlada desde backoffice
- `Pagos` concentra comprobantes manuales
- `Pedidos > Operacion` concentra la trazabilidad comercial del pedido y la confirmacion controlada
- la frontera de gateway online queda solo como capacidad futura y no modifica el comportamiento actual del storefront

## Problema de negocio que resuelve este slice

Huelegood necesita poder seguir vendiendo desde el storefront propio con evidencia de pago, revision humana y trazabilidad suficiente para operacion, auditoria y despacho, sin depender todavia de una conciliacion automatica estable de pasarela online.

## Actores y roles implicados

| Actor / rol | Responsabilidad en este slice |
| --- | --- |
| `cliente` | arma carrito, completa identidad, elige entrega, paga por billetera virtual y sube comprobante |
| storefront web | guia el wizard, cotiza, valida datos minimos y envia el request de checkout |
| API Huelegood | recalcula quote, crea pedido/pago, persiste evidencia y expone estados consistentes |
| `operador_pagos` | revisa comprobantes manuales y deja decision operativa |
| `admin` | puede resolver manualmente y auditar el cierre comercial |
| worker | ejecuta decisiones operativas idempotentes y dispara efectos asincronos |
| notificaciones | informa resultado al cliente y a equipos internos |
| provider online futuro | frontera de adaptador idempotente; no superficie activa del checkout hoy |

Roles habilitados segun matriz vigente:

- `cliente` sobre su propio checkout y evidencia
- `operador_pagos`, `admin` y `super_admin` para resolver pagos manuales
- `ventas` solo consulta contexto del pedido; no resuelve pagos

## Flujo funcional consolidado

### 1. Checkout publico

1. El cliente agrega una de las referencias activas al checkout.
2. La web cotiza subtotal, shipping y total con las reglas vigentes.
3. El cliente completa documento, identidad, entrega, ubigeo y contacto.
4. La API intenta reutilizar identidad por `documentType + documentNumber`.
5. Si no existe coincidencia local y el documento es `DNI`, la API consulta `ApiPeru` y autocompleta nombre.
6. El paso final expone solo el camino de pago manual visible hoy.

### 2. Pago manual con comprobante

1. El cliente ve la instruccion de billetera virtual.
2. El cliente realiza el pago externo y abre el modal de comprobante.
3. El cliente sube evidencia en formato valido.
4. El request del checkout crea pedido, pago y solicitud manual asociada, preservando el estado vigente del runtime.
5. El pedido queda pendiente de revision operativa.

### 3. Conciliacion operativa manual

1. `operador_pagos` o `admin` revisa el caso.
2. El backoffice separa el caso en la bandeja correcta.
3. Si el caso es `manual`, la revision parte en `Pagos`.
4. Si la decision es positiva, la plataforma deja el pago como `paid` y el pedido como `confirmed`.
5. Si la decision es negativa, el sistema registra motivo, mantiene trazabilidad y aplica la politica operativa sobre reintento, expiracion o cancelacion.

## Requerimientos funcionales

### RF-01. Identidad documental obligatoria

- todo checkout exige tipo y numero de documento
- el backend es la autoridad final para lookup y normalizacion del cliente
- `DNI` sin coincidencia local debe consultarse contra `ApiPeru`

### RF-02. Entrega y direccion normalizadas

- la direccion publica se guarda con departamento, provincia y distrito de Peru
- `delivery` estandar solo permite provincia de Lima y Callao
- envio a provincia solo permite `Shalom` y requiere sucursal de recojo
- el flete a provincia no se cobra en el checkout

### RF-03. Pago manual visible y trazable

- el paso 3 del wizard solo expone pago manual visible hoy
- el numero y titular de la billetera deben verse antes de abrir el modal
- el cliente puede subir uno o mas comprobantes segun la politica vigente
- la evidencia debe quedar asociada a una solicitud operativa, no solo a una transaccion suelta

### RF-04. Revision humana obligatoria

- no se confirma un pago manual sin revision humana en MVP
- toda decision deja actor, fecha, observacion y referencia
- la decision debe reflejarse en pedido, pago, historial y auditoria

### RF-05. Separacion de responsabilidades operativas

- `Pagos` es dueno de la bandeja de comprobantes manuales
- `Pedidos > Operacion` es la vista canonica de trazabilidad comercial del pedido
- `Pagos` no reemplaza el detalle operativo del pedido
- `Pedidos > Operacion` no debe mezclar registro manual directo con revision de comprobantes sin una ruta explicita

### RF-06. Frontera futura de gateway online

- puede existir un solo provider online activo a la vez
- el adaptador futuro debe operar con idempotencia
- la confirmacion automatica futura solo sera valida en estados externos equivalentes a `captured` o `paid`
- mientras esa capacidad no exista de forma estable, el cierre comercial sigue siendo manual

## Requerimientos no funcionales

- idempotencia en creacion de pedido o resolucion operativa
- evidencias privadas, no publicas por URL abierta
- auditoria de actor, fecha, referencia y notas
- mensajes entendibles para cliente; detalles tecnicos quedan fuera de la UI publica
- compatibilidad desktop/mobile del wizard
- trazabilidad suficiente para soporte, pagos, despacho y comisiones

## Reglas canonicas del slice

- la UI publica actual no expone cupones, codigos de vendedor ni pasarela online visible
- ambos caminos de cobro deben converger en el mismo agregado `order`, aunque solo el manual este visible hoy
- un pedido conserva snapshot comercial y de direccion aunque luego cambie el catalogo
- la resolucion final del pedido no depende de que el cliente vea estados internos de pago
- una solicitud ya aprobada o rechazada no debe procesarse dos veces
- `Openpay` y cualquier reemplazo futuro viven detras de una frontera de proveedor; no gobiernan el flujo documental vigente de Fase 1

El detalle operativo queda consolidado en [reglas/checkout-y-pagos.md](./reglas/checkout-y-pagos.md).

## Riesgos y tensiones del estado actual

- el runtime actual del checkout manual crea el pedido al confirmar el modal con comprobante, por lo que la reserva de stock ocurre tarde; este riesgo se documenta, no se redefine aqui
- la documentacion historica sigue mencionando `Openpay` como camino visible principal, pero el storefront vigente ya prioriza pago manual
- si operacion mezcla `Pagos` y `Pedidos > Operacion`, se pierde claridad sobre quien revisa evidencia y quien confirma trazabilidad comercial

## Criterios de aceptacion del slice documental

- existe un documento rector de Fase 1 que fija alcance, actores, reglas y frontera futura
- existen casos de uso separados para checkout publico, pago manual con comprobante y conciliacion operativa manual
- la responsabilidad de `Pagos` y `Pedidos > Operacion` queda explicitamente diferenciada
- el gateway online se documenta solo como frontera futura idempotente
- la UX de Fase 2 puede derivarse sin contradecir el estado publico actual del checkout
