# Fase 2 - Pipeline Comercial Amplio UX/UI

## Objetivo

Formalizar la ampliacion del slice `011-pipeline-comercial-amplio` como una
extension real del workbench comercial dentro de `/crm`, agregando lenguaje
de pipeline amplio sobre `customer_relationship_case` con `pipelineStage`,
`priority`, `commercialChannel`, `followUpAt` y `lastPipelineActivityAt`,
sin vender kanban, oportunidades ni una app nueva.

## Fuentes de runtime

- `apps/admin/app/crm/page.tsx`
- `apps/admin/components/crm-workspace.tsx`
- `apps/admin/lib/api.ts`
- `packages/shared/src/types/api.ts`

## Dependencias del slice

- `docs/fase-2-ux-ui/02.09-crm-transversal-por-cliente-ux-ui.md`
- `specs/010-crm-transversal-por-cliente/product-design.md`
- `specs/010-crm-transversal-por-cliente/spdd-frontend.md`
- `docs/superpowers/specs/2026-05-29-huelehuele-pipeline-comercial-amplio-design.md`

## Superficies

### Superficie principal

- detalle del cliente dentro de `/crm`
- sigue siendo la superficie natural del `customer_relationship_case`
- mantiene `commercialOwner`, `assignee`, `followUpAt`, timeline y contexto
  read-only de cliente, pedidos y casos previos
- suma un resumen visible del pipeline con `pipelineStage`, `priority`,
  `commercialChannel` y `lastPipelineActivityAt`
- permite cierres manuales `won` y `lost` como parte del mismo workbench
- no se convierte en `commercial_opportunity`, forecast ni CRM separado

### Superficie secundaria

- bandeja comercial filtrable dentro de `/crm`
- se presenta como tabla o lista filtrable, no como kanban en este corte
- reutiliza el patron visible ya existente en `crm-workspace.tsx`:
  metricas, busqueda, filtros y `AdminDataTable`
- expone filtros por `commercialOwner`, `assignee`, `pipelineStage`,
  `priority`, `commercialChannel` y `status`
- expone vistas de pendientes de hoy y vencidos usando `followUpAt`
- ordena la cola comercial sin leer todo el timeline gracias a
  `lastPipelineActivityAt`
- no abre una ruta nueva ni una bandeja fuera de `/crm`

## Elementos visibles clave

- metricas cortas de volumen operativo, pendientes de hoy, vencidos,
  cierres `won` y cierres `lost`
- busqueda por cliente y filtros combinables para reducir la cola
- columnas o bloques visibles para `commercialOwner`, `assignee`,
  `pipelineStage`, `priority`, `commercialChannel`, `status`,
  `followUpAt` y `lastPipelineActivityAt`
- badges o labels que separan claramente `status` operativo de
  `pipelineStage` comercial
- lectura rapida de la proxima accion comercial sin duplicar la historia
  completa del timeline
- accion manual para mover etapa y registrar cierre `won` o `lost`
- cierre `lost` con captura explicita de `lostReason`
- visibilidad de `lastPipelineActivityAt` como senal de actividad reciente,
  distinta de `followUpAt`
- trazabilidad visible de cambios de etapa dentro del timeline del caso

## Guardrails UX

- el slice vive dentro de `/crm`; no abre aplicacion, modulo ni ruta nueva
- la bandeja secundaria es tabla o lista filtrable primero; no se promete
  kanban complejo
- `status` y `pipelineStage` deben verse como ejes distintos del mismo caso
- `followUpAt` sigue siendo la unica fecha objetivo operativa del caso
- `lastPipelineActivityAt` ordena actividad reciente, pero no compite con
  `followUpAt`
- `commercialChannel` expresa el canal principal del caso, no cada contacto
  del timeline
- `won` y `lost` son cierres manuales del pipeline, no cierres tecnicos
  automaticos
- `lost` no debe cerrarse sin `lostReason`
- `won` no debe cerrarse sin nota y evidencia
- la UX no debe sugerir scoring, forecast, automatizaciones ni subpipelines
  por canal
- el workbench debe sentirse como ampliacion seria de `010`, no como un
  rename del runtime actual

## Regla UX critica

- el usuario debe entender que sigue operando el mismo cliente canonico en
  `/crm`, ahora con una cola comercial mas amplia y ordenable
- `commercialOwner`, `assignee`, `pipelineStage`, `priority`,
  `commercialChannel`, `followUpAt` y `lastPipelineActivityAt` deben leerse
  juntos como disciplina comercial minima
- la UI no debe vender el slice como CRM enterprise nuevo, campaigns ni
  pipeline visual independiente

## Criterio de cierre

- `011` queda documentado como ampliacion natural del workbench definido en
  `010`
- la bandeja comercial secundaria queda defendida como tabla o lista
  filtrable dentro de `/crm`
- el slice deja explicito que `won` y `lost` viven sobre el mismo
  `customer_relationship_case` y no abren una entidad comercial nueva
