## Premisas
- El producto ya existe y ya opera.
- El template aporta estructura canonica, no relato ficticio de arranque.
- La documentacion vigente actual se conserva hasta que su equivalente canonico
  cubra el mismo alcance.

## Capas de trabajo
| Capa | Proposito |
|---|---|
| Raiz canonica | Fijar estado, mapa, trazabilidad, glosario y reglas de trabajo. |
| Fase 0 | Consolidar vision, roadmap, estimacion, roles y checklist del brownfield. |
| Fases 1 a 3 | Reordenar requerimientos, UX y arquitectura ya existentes en el repo. |
| Fases 5 a 8 | Backfill de construccion, QA, deploy y operacion sobre el runtime real. |

## Secuencia propuesta
1. Crear mapa brownfield y raiz canonica.
2. Backfillear Fase 0 con contenido de negocio ya vigente.
3. Formalizar Fases 1 a 3 sin borrar `docs/flows/`, `docs/ux/` ni
   `docs/architecture/` hasta que cada capa cierre.
4. Formalizar Fases 5 a 8 usando codigo, deploy y release reales como evidencia.
5. Solo despues decidir que documentos previos pueden quedar historicos.

## Guardrails
- No usar lenguaje de greenfield para explicar decisiones ya operativas.
- No mover el source of truth fuera del codigo vivo ni del documento vigente
  que hoy lo explica.
- No reabrir arquitectura, alcance o roadmap solo por acomodarlos al template.
- Cada nuevo documento canonico debe decir de donde sale su contenido.

## Definicion de done para esta etapa
- La raiz canonica existe.
- Fase 0 existe y esta instanciada al dominio Huelegood.
- El mapa brownfield deja claro que manda hoy y que queda pendiente.
- Los siguientes frentes pueden avanzar sin ambiguedad sobre entradas,
  limites y vocabulario.
