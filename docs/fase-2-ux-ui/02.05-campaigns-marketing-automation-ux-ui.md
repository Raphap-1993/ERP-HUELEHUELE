# Fase 2 - UX/UI Campaigns Marketing Automation

## Objetivo

Formalizar la UX operativa vigente de `/admin/marketing` sin convertir este
slice en un journey builder, un CRM ampliado ni un rediseño del runtime
actual.

## Fuentes de runtime

- `apps/admin/app/marketing/page.tsx`
- `apps/admin/components/marketing-workspace.tsx`
- `apps/admin/lib/api.ts`
- `apps/api/src/modules/marketing/marketing.controller.ts`
- `apps/api/src/modules/marketing/marketing.service.ts`
- `apps/api/src/modules/notifications/notifications.service.ts`
- `apps/worker/src/main.ts`

## Superficies

### `/admin/marketing`

- es la superficie operativa principal del slice
- abre con metricas de campanas cargadas: total, activas, programadas y
  completadas
- ofrece una CTA unica `Nueva campana`
- muestra tabla de campanas con `segmentName`, `channel`, `status`,
  `runStatus`, `recipients` y `scheduledAt`
- muestra tabla read-only de plantillas con `channel`, `subject`, `status` y
  `updatedAt`
- resuelve carga y error con mensajes inline simples
- no muestra hoy tabla de segmentos, historial de campana ni timeline de
  eventos

### Modal `Nueva campana`

- captura `name`, `goal`, `segmentId`, `templateId`, `channel` y
  `scheduledAt`
- preselecciona el primer segmento y la primera plantilla disponibles cuando
  el catalogo carga
- permite corrida inmediata si `scheduledAt` queda vacio
- permite programacion basica si `scheduledAt` viene informado
- muestra un resumen corto del segmento elegido con nombre y `audienceSize`
- muestra un resumen corto de la plantilla elegida con nombre y `subject`
- no expone editor de cuerpo, builder de journey ni simulacion de entrega

### Catalogos read-only `segments` y `templates`

- `segments` se consumen como dropdown operativo con previsualizacion minima
  de audiencia
- `definition` y `status` del segmento existen en API pero no se renderizan
  hoy en la UI
- `templates` se consumen como selector de creacion y como tabla de consulta
  read-only
- el `status` de plantilla si es visible en la tabla, pero no bloquea por si
  mismo la creacion desde esta pantalla
- el slice no abre authoring completo ni lifecycle propio para estos
  catalogos

### Eventos y frontera de entrega

- el page shell nombra `eventos`, y la API expone `GET /admin/campaigns/events`
- el workspace actual no consume `fetchCampaignEvents()` ni renderiza una tabla
  visible de eventos en `/admin/marketing`
- la cola y la entrega tecnica viven fuera de esta superficie, en
  `notifications` y `worker`
- por eso `/admin/marketing` comunica estado operativo de campana, no
  resultado tecnico final de dispatch

## Estados visibles y semantica actual

- `status` de campana se presenta con badges y puede verse como `draft`,
  `scheduled`, `running`, `completed` o `cancelled` si existe en datos
- `runStatus` se presenta con badges y puede verse como `queued`, `running`,
  `completed` o `failed`
- `status` de plantilla se ve como `active`, `draft` o `archived`
- `status` de segmento existe a nivel de contrato, pero no tiene
  representacion visible actual en la pantalla

## Contrato UX del slice

- `campaigns` es el agregado visible principal del workbench
- la creacion usa catalogos read-only existentes y deja el detalle authorable
  fuera de esta UX
- `scheduledAt` es el unico mecanismo visible de scheduling del slice
- la campana creada queda como registro operativo con snapshot congelado de
  segmento, plantilla y destinatarios, aunque ese snapshot completo no se
  inspecciona hoy en la UI
- la superficie no promete journeys, analytics avanzados ni CRM ampliado
- la entrega real del mensaje no se gobierna ni se observa desde esta pantalla

## Regla UX critica

- `/admin/marketing` debe sentirse como workbench operativo simple de
  campanas, no como automation suite completa
- la seleccion de segmento y plantilla valida dependencias minimas reales del
  runtime sin inventar gates de negocio nuevos
- la frontera `marketing -> notifications -> worker` debe quedar explicita
  para no confundir corrida de campana con entrega tecnica confirmada

## Criterio de cierre

- `/admin/marketing` queda documentado como superficie principal del slice
- los catalogos read-only, estados visibles y scheduling basico quedan
  nombrados sin redisenar el runtime
- la ausencia actual de eventos visibles en la UI y la frontera hacia
  `notifications/worker` quedan explicitadas sin sobreprometer
