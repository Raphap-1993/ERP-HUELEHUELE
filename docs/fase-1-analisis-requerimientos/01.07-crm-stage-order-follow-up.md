# Fase 1 - CRM Stage Order Follow-Up

## Objetivo

Homologar el seguimiento operativo derivado del pedido que hoy vive en
`orders`, formalizando `crmStage`, `commercialTrace` y la vista
`Pedidos > Operacion` sin convertir el slice en CRM manual ni absorber
clientes, fulfillment o notifications como ownership principal.

## Alcance del slice

### Dentro de alcance

- `orders` como agregado operativo principal
- `Pedidos > Operacion` como superficie visible principal
- `crmStage` derivado desde `orderStatus` y `paymentStatus`
- `commercialTrace` como puente comercial de confirmacion
- `CommercialTraceCard`
- rutas `manual_direct`, `manual_request`, `openpay_backoffice` y
  `openpay_provider`
- estados `pending`, `confirmed` y `rejected`
- cierre `closed` cuando el pedido llega a `Delivered` o `Completed`
- cierre negativo cuando el pedido cae y `crmStage` se limpia
- side effects secundarios de notificacion disparados por confirmacion o
  rechazo comercial

### Fuera de alcance

- maestro de clientes
- conflictos de identidad
- notas manuales de seguimiento
- tareas comerciales
- timeline CRM completo
- fulfillment
- dispatch
- vendor assignment
- dashboard
- notifications como owner principal

## Estado actual que se conserva

- `Pedidos > Operacion` ya expone `Etapa CRM`, `Seguimiento` y
  `CommercialTraceCard`
- el runtime actual ya usa `CrmStage.ReadyForFollowUp`,
  `CrmStage.FollowUp` y `CrmStage.Closed`
- `crmStage` ya se deriva desde `orderStatus` y `paymentStatus`
- `commercialTrace` ya modela rutas `manual_direct`, `manual_request`,
  `openpay_backoffice` y `openpay_provider`
- `commercialTrace` ya modela estados `pending`, `confirmed` y `rejected`
- la aprobacion manual y la conciliacion Openpay ya dejan el pedido listo
  para seguimiento CRM
- el rechazo manual ya limpia `crmStage` y conserva la traza comercial de
  rechazo
- el runtime ya diferencia el ownership operativo de `Ventas` y el papel
  acotado de `OperadorPagos` en la conciliacion
- notifications ya aparecen como side effect tecnico, no como agregado del
  slice

## Problema de negocio que resuelve este slice

Huele Huele necesita fijar una narrativa canonica para el seguimiento
operativo derivado del pedido: cuando un cobro o una decision operativa deja
la venta lista para seguimiento, como queda registrada la ruta comercial que
la confirmo o rechazo y donde termina el ownership de `orders` para no
mezclar este slice con CRM manual, clientes o fulfillment.

## Actores y roles implicados

| Actor / rol | Responsabilidad en este slice |
| --- | --- |
| ventas | owner operativo principal del seguimiento del pedido |
| operador_pagos | empuja transiciones de cobro y conciliacion que dejan el pedido listo o no para seguimiento |
| admin | soporte transversal y override operativo |
| super_admin | acceso total para recuperacion y soporte avanzado |
| orders | agregado principal del slice y fuente de `crmStage` y `commercialTrace` |
| notifications | side effect tecnico secundario cuando la confirmacion o rechazo genera email o evento |

Roles habilitados segun matriz vigente:

- `ventas` como owner operativo principal del slice
- `operador_pagos`, `admin`, `super_admin` y `seller_manager` con acceso
  tecnico a `orders` segun `adminAccessRoles.orders`

## Modulos y superficies implicadas

- backoffice `Pedidos > Operacion`
- `orders`
- `payments` como frontera de confirmacion y rechazo comercial
- `notifications` solo como side effect secundario
- auditoria administrativa sobre acciones de conciliacion y cierre

## Flujo funcional consolidado

### 1. Derivacion de etapa CRM del pedido

1. El pedido cambia de estado o de situacion de pago.
2. `orders` recalcula `crmStage`.
3. El pedido queda en `ready_for_followup`, `followup`, `closed` o sin etapa.
4. `Pedidos > Operacion` refleja la etapa y el seguimiento sin edicion manual.

### 2. Confirmacion comercial y traza operativa

1. Una ruta de cobro o una decision operativa confirma o rechaza
   comercialmente el pedido.
2. `orders` registra o recalcula `commercialTrace`.
3. La ruta queda como `manual_direct`, `manual_request`,
   `openpay_backoffice` u `openpay_provider`.
4. La traza conserva `status`, `actor`, `reference`, `note` y evidencia
   cuando aplica.

### 3. Cierre derivado del seguimiento

1. El pedido avanza a `Delivered` o `Completed`.
2. `orders` deriva `crmStage = closed`.
3. `Pedidos > Operacion` muestra el cierre del seguimiento.
4. Si el pedido cae o el pago falla, `crmStage` se limpia y
   `commercialTrace` conserva el cierre comercial rechazado.

## Requerimientos funcionales

### RF-01. `orders` es el agregado principal

- la unidad operativa principal del slice es el pedido
- `crmStage` y `commercialTrace` viven en `orders`
- el slice no abre un agregado CRM paralelo para el mismo problema

### RF-02. `crmStage` es estado derivado `as-is`

- `crmStage` no es editable manualmente como workflow
- la derivacion depende de `orderStatus` y `paymentStatus`
- el runtime usa `ready_for_followup`, `followup` y `closed`

### RF-03. `commercialTrace` es puente comercial de confirmacion

- `commercialTrace` no es una bitacora completa de CRM
- la traza explica la ruta y el hito comercial del pedido
- el runtime usa `pending`, `confirmed` y `rejected`

### RF-04. Rutas comerciales canonicas

- el slice conserva `manual_direct`
- el slice conserva `manual_request`
- el slice conserva `openpay_backoffice`
- el slice conserva `openpay_provider`

### RF-05. `Pedidos > Operacion` es la superficie visible principal

- la vista expone `Etapa CRM`
- la vista expone `Seguimiento`
- la vista expone `CommercialTraceCard`
- la vista no se convierte en un CRM manual de tareas o contactos

### RF-06. Ownership operativo explicito

- `ventas` es owner operativo principal del seguimiento
- `operador_pagos` solo empuja transiciones de cobro y conciliacion
- `admin` y `super_admin` actuan como override

### RF-07. Relacion explicita entre `crmStage` y `commercialTrace`

- `commercialTrace` explica la ruta y el hito comercial
- `crmStage` resume el punto operativo/comercial derivado del pedido
- ambas senales se leen juntas en la operacion, sin perder fronteras

### RF-08. Cierre positivo y cierre negativo

- `Delivered` y `Completed` derivan `crmStage = closed`
- si el pedido cae, se cancela o el pago falla, `crmStage` se limpia
- `commercialTrace` conserva la evidencia comercial del cierre rechazado

### RF-09. Notifications como side effect secundario

- ciertas confirmaciones o rechazos pueden disparar email o eventos
- el ownership principal del slice sigue en `orders`
- el slice no mueve el dominio a `notifications`

## Requerimientos no funcionales

- trazabilidad de actor, referencia, nota y evidencia en la traza comercial
- consistencia entre estado del pedido, estado de pago y `crmStage`
- semantica estable entre backoffice, API y tipos compartidos
- claridad de ownership entre `ventas`, `operador_pagos` y `orders`
- preservacion de los side effects tecnicos sin convertirlos en dominio
  principal

## Reglas canonicas del slice

- `orders` es el agregado principal
- `Pedidos > Operacion` es la superficie visible principal
- `ventas` es owner operativo principal
- `operador_pagos` solo empuja transiciones de cobro
- `crmStage` es estado derivado `as-is`, no workflow editable manualmente
- `crmStage` usa `ready_for_followup`, `followup` y `closed`
- `commercialTrace` es puente comercial de confirmacion, no bitacora completa
  de CRM
- `commercialTrace` usa `manual_direct`, `manual_request`,
  `openpay_backoffice` y `openpay_provider`
- `commercialTrace` usa `pending`, `confirmed` y `rejected`
- `commercialTrace.pending` forma parte del runtime canonico
- el cierre negativo limpia `crmStage` y conserva `commercialTrace.rejected`
- notifications solo entra como side effect secundario
