# Fase 1 - Automatizacion Comercial Amplia

## Objetivo

Homologar journeys comerciales multi-step sobre
`customer_relationship_case`, con binding estable a la oportunidad activa
cuando aplique, templates cerrados, waits, condiciones simples, pasos
manuales y side effects seguros sin abrir inbox, chaining entre journeys ni
builder libre.

## Estado actual que se conserva

- `010` ya fijo `customer_relationship_case` como ancla del trabajo
  comercial transversal del cliente.
- `011` ya fijo `pipelineStage`, `priority`, `commercialChannel` y la cola
  comercial amplia del caso.
- `012` ya fijo scoring y automatizaciones simples con catalogo cerrado de
  reglas y acciones seguras.
- `013` ya fijo `commercial_opportunity` como deal puntual con lifecycle y
  valor esperado propios.
- `/crm` ya es la superficie operativa central para `ventas` y `marketing`.
- `worker` y la frontera de campañas/notificaciones ya existen como runtime
  reutilizable, pero sin canon de journeys multi-step.

## Problema de negocio que resuelve este slice

Huele Huele ya tiene workbench comercial por cliente, pipeline manual,
scoring y deal puntual, pero todavia le falta la capa de orquestacion
multi-step que conecte triggers, waits, pasos manuales y side effects
seguros dentro del mismo `/crm`. El gap no es abrir una plataforma libre de
workflow, sino formalizar journeys cerrados y auditables para recuperacion,
reactivacion y avance comercial.

## Actores y roles implicados

| Actor / rol | Responsabilidad en este slice |
| --- | --- |
| marketing | owner del catalogo de journey templates |
| ventas | consumidor operativo principal de efectos y pasos manuales |
| admin | override transversal del modulo |
| super_admin | soporte y recuperacion avanzada |
| customers | dominio ancla de `customer_relationship_case` y del contexto comercial |
| worker | scheduler y continuacion diferida de waits y timers |

Roles habilitados segun matriz vigente:

- `marketing` mantiene ownership del catalogo de templates.
- `ventas` resuelve pasos humanos y consume la automatizacion en `/crm` como
  owner operativo principal.
- `marketing` puede resolver pasos humanos de forma secundaria cuando el
  template o el flujo lo requieran.
- `admin` y `super_admin` actuan como override.
- `worker` no adquiere ownership comercial; solo ejecuta continuaciones
  diferidas y side effects ya aprobados.

## Flujo funcional consolidado

### 1. Instanciacion y arranque del journey

1. Ocurre un trigger canonico elegible para un template cerrado.
2. El sistema valida elegibilidad del caso y que no exista otra instancia
   no terminal del mismo `template + customer_relationship_case`.
3. Se crea la instancia con snapshot del template.
4. El journey ejecuta pasos inmediatos `inline`.
5. Si aparece un `wait`, la continuacion queda delegada a `worker/BullMQ`.

### 2. Waits, pasos manuales y reanudacion

1. Una instancia activa puede alcanzar un `wait`, una `condition` o un paso
   `manual_review`.
2. El paso manual bloquea la continuacion del journey.
3. `ventas` lo resuelve desde `/crm` como owner operativo principal.
4. `marketing` puede resolverlo de forma secundaria cuando el template o el
   flujo lo requieran.
5. Al resolverse el paso manual, la instancia reanuda automaticamente si no
   queda otra condicion pendiente.
6. Los waits, timers y reanudaciones diferidas se resuelven via `worker`.

### 3. Cierre, cancelacion y reentrada

1. Una instancia puede completar por exito o cancelarse por
   incompatibilidad fuerte.
2. Si la incompatibilidad es blanda, la instancia puede pausarse o desviar
   su camino.
3. Mientras una instancia siga `active` o `paused`, no puede nacer otra del
   mismo `template + case`.
4. El template puede reingresar sobre el mismo caso segun su politica y
   `reentryCooldown`.
5. Si la instancia estaba ligada a una oportunidad activa, mantiene binding
   estable al deal original.
6. Toda transicion y todo paso dejan traza obligatoria en el timeline del
   caso.

## Requerimientos funcionales

### RF-01. `014` vive sobre el caso comercial del cliente

- el journey se ancla a `customer_relationship_case`
- el caso del cliente sigue siendo el agregado comercial principal
- la oportunidad activa es solo contexto ligado cuando el template la exige
- el engine no usa `commercial_opportunity` como agregado raiz

### RF-02. Catalogo cerrado de templates

- los templates canonicos son `followup_recovery`, `reactivation_nurture`,
  `opportunity_progression` y `post_loss_recovery`
- cada template declara elegibilidad explicita
- cada template puede definir `reentryCooldown`
- cada instancia toma snapshot del template al arrancar

### RF-03. Instanciacion controlada

- el journey puede nacer por auto-start de trigger canonico
- el journey puede lanzarse manualmente de forma excepcional por `ventas` o
  `marketing`
- solo puede existir una instancia no terminal por `template + case`
- el mismo caso puede tener varios journeys activos si son templates
  distintos
- una instancia `paused` sigue bloqueando la creacion de otra del mismo
  `template + case`

### RF-04. Estado propio de instancia

- la instancia usa `active`, `paused`, `completed` y `cancelled`
- puede pausarse y reanudarse manualmente
- puede completar automaticamente por exito
- puede cancelarse automaticamente por incompatibilidad fuerte
- si el caso padre queda `dormant`, la instancia pasa a `paused`
- si el caso padre queda `resolved`, la instancia termina como `completed` o
  `cancelled` segun su objetivo

### RF-05. Tipos de paso cerrados

- `wait`
- `condition`
- `create_followup_task`
- `manual_review`
- `suggest_priority`
- `enqueue_existing_campaign`
- `mark_journey_milestone`

Reglas:

- no hay scripting libre
- no hay chaining entre journeys
- las condiciones solo usan senales canonizadas del caso y de la oportunidad

### RF-06. Acciones automaticas seguras

- el journey puede crear tarea de follow-up
- el journey puede sugerir prioridad
- el journey puede encolar una campana existente
- el journey puede marcar hitos
- el journey no muta automaticamente `pipelineStage`, `status` ni
  `opportunityStage`
- el journey no crea oportunidades automaticamente

### RF-07. Binding estable con oportunidad activa

- si el journey queda ligado a una oportunidad activa, el binding se
  mantiene estable al deal original
- el journey no hace rebind silencioso a otra oportunidad futura
- si el deal deja de aplicar, se evalua incompatibilidad fuerte o blanda

### RF-08. Pasos manuales bloqueantes

- `manual_review` crea un paso humano pendiente
- el paso manual bloquea la continuacion del journey
- `ventas` lo resuelve como owner operativo principal dentro de `/crm`
- `marketing` puede resolverlo de forma secundaria cuando el template o el
  flujo lo requieran
- al resolverse, la instancia reanuda automaticamente si no queda otra
  condicion pendiente

### RF-09. Reentrada controlada

- el mismo template puede volver a instanciarse sobre el mismo caso despues
  de `completed` o `cancelled`
- la reentrada respeta `reentryCooldown` por template
- la politica de reentrada depende del template y de sus estados terminales
  permitidos

### RF-10. Trazabilidad obligatoria

- inicio, pausa, reanudacion, branch, paso automatico, paso manual creado o
  resuelto, cancelacion y completion quedan trazados
- la traza vive en el mismo workbench de `/crm`
- no hace falta consola separada para reconstruir la ejecucion del journey

## Resultado esperado

El slice `014-automatizacion-comercial-amplia` deja formalizada la capa
minima de journeys comerciales multi-step sobre el cliente canonico,
reutilizando `worker`, campañas existentes y pasos humanos dentro de `/crm`
sin abrir todavia una plataforma generalista de workflows.
