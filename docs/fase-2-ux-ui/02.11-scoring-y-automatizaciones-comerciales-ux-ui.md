# Fase 2 - Scoring Y Automatizaciones Comerciales UX/UI

## Objetivo

Formalizar la UX operativa del slice `012-scoring-y-automatizaciones-comerciales`
como una extension del workbench comercial dentro de `/crm`, agregando tier
visible `cold/warm/hot`, razon corta del score, sugerencias y trazabilidad de
automatizaciones simples sin abrir una consola nueva ni vender un engine de
journeys.

- `apps/admin/lib/api.ts`

## Superficies

### Superficie principal

- detalle del cliente dentro de `/crm`
- sigue siendo la superficie natural del `customer_relationship_case`
- conserva resumen comercial, `pipelineStage`, `priority`, `commercialChannel`,
  `nextStep`, `followUpAt`, timeline y tareas ya canonizadas
- suma score visible del caso, razon corta, sugerencia de prioridad y
  trazabilidad de automatizaciones simples
- no se convierte en una consola nueva de automation ni en un dashboard
  separado

### Superficie secundaria

- misma bandeja comercial filtrable dentro de `/crm`
- puede exponer lectura rapida de `scoreTier` junto a `pipelineStage`,
  `priority`, `status` y `followUpAt`
- puede resaltar candidatos de follow-up, tareas automaticas y efectos
  recientes sin sacar al usuario de la cola comercial
- no abre ruta separada, builder libre ni vista de journeys

### Gestion operativa minima

- configuracion minima del catalogo cerrado de reglas en backoffice, si el
  runtime la expone
- esa gestion no es la promesa visual principal del slice
- el foco UX sigue estando en como `ventas` y `marketing` consumen resultados
  dentro de `/crm`

## Contrato UX visible minimo

- el score visible usa solo `cold`, `warm` y `hot`
- la UI no muestra el puntaje interno
- cada tier debe ir acompanado de una razon corta del score
- `scoreTier` no reemplaza `priority`; solo la complementa
- si existe sugerencia de prioridad, debe verse como sugerencia y no como
  cambio automatico ya aplicado
- las tareas automaticas deben sentirse como parte del mismo workbench del
  cliente
- la trazabilidad de side effects debe distinguir claramente entre senal,
  sugerencia y accion ejecutada
- si una regla encola una campaign existente, la UI debe leerlo como efecto
  derivado del caso y no como authoring de campañas desde `/crm`

## Elementos visibles clave

- badge o label de `scoreTier`
- razon corta del score junto al resumen comercial del caso
- marca visible de sugerencia de prioridad cuando aplique
- indicador de candidato de follow-up cuando exista evento derivado relevante
- tareas o recordatorios automaticos en la misma zona operativa del caso
- timeline o traza visible de automatizaciones simples evaluadas o ejecutadas
- lectura rapida de ultimos efectos sin abrir otra consola

## Lecturas secundarias o derivadas

- `score_changed` es lectura derivada visible del caso, no un flujo aparte
- `followup_candidate_detected` sirve para resaltar trabajo comercial pendiente
  y no para mover automaticamente `pipelineStage` o `status`
- las acciones encoladas al worker siguen siendo secundarios al caso comercial;
  su valor UX es evidenciar que el sistema actuó, no trasladar ownership fuera
  de `/crm`
- la deduplicacion y el `cooldown` pueden traducirse en estados de "omitido" o
  "no repetido" dentro de la traza, sin obligar a exponer debug tecnico crudo

## Guardrails UX

- el slice vive dentro de `/crm`; no abre app, ruta ni bandeja nueva
- la UI no debe sugerir que el score sea editable manualmente
- la UI no debe mostrar numeros, formulas ni detalle tecnico del puntaje
- la UI no debe implicar que las automatizaciones cambian `pipelineStage`,
  `status`, `commercialOwner` o `assignee`
- la UI no debe vender journeys, forecast, opportunities ni IA comercial
- el catalogo de reglas, si se muestra, debe sentirse cerrado y administrable,
  no como builder libre

## Regla UX critica

- el usuario debe entender que sigue operando el mismo cliente canonico dentro
  de `/crm`, ahora con una capa derivada de prioridad comercial y automatizacion
  simple
- `scoreTier`, razon visible, sugerencia de prioridad, tareas automaticas y
  trazabilidad deben leerse como ayudas operativas del mismo caso, no como un
  modulo paralelo
- la UX no debe vender el slice como plataforma de marketing automation
  completa

## Criterio de cierre

- `012` queda documentado como una extension natural del workbench definido en
  `010` y `011`
- la bandeja de `/crm` queda defendida como lugar de consumo del score y de los
  efectos simples
- el slice deja explicito que la operacion visible es score + sugerencias +
  side effects acotados, no journeys ni engine libre
