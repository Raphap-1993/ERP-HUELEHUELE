# Fase 1 - Customers Identity Conflicts

## Objetivo

Homologar el modulo `customers` y la superficie `/crm` vigentes de Huele
Huele como bounded context del maestro canonico de clientes, sin convertirlo
en CRM amplio ni absorber `crmStage` o el seguimiento comercial de pedidos.

## Alcance del slice

### Dentro de alcance

- `customers` como agregado operativo principal
- `/crm` como superficie visible del slice
- alta manual de cliente
- edicion de perfil
- estado del cliente
- direcciones
- contrasena temporal al crear
- lectura de pedidos recientes dentro del detalle del cliente
- deteccion de conflictos de identidad
- resolucion operativa de conflictos
- acciones `assign_existing`, `merge` e `ignore`
- merge de clientes con destino canonico
- clientes sinteticos o regularizados desde pedidos
- eliminacion operativa existente como capacidad excepcional

### Fuera de alcance

- `crmStage`
- seguimiento comercial de pedidos
- campaigns
- wholesale
- loyalty
- scoring comercial avanzado
- timeline comercial transversal
- portal cliente
- reescritura arbitraria de snapshots historicos de `orders`

## Estado actual que se conserva

- `/crm` ya expone el workbench operativo de clientes en el dominio admin
- la API ya expone CRUD de clientes, conflictos, merge y resolucion bajo
  `/admin/customers`
- el runtime actual ya lista clientes, conflictos abiertos, detalle, create,
  edit, merge y delete
- `customers` ya persiste el perfil vivo del cliente con estado, direcciones y
  opt-in de marketing
- el detalle de cliente ya muestra pedidos recientes como contexto operativo
- el runtime ya admite clientes sinteticos o regularizados desde pedidos
- la deteccion de identidad ya combina documento, email, telefono y senales
  mas debiles como nombre mas direccion
- el runtime actual ya usa `assign_existing`, `merge` e `ignore` para resolver
  conflictos
- `mergeCustomersInternal()` ya rechaza documentos canonicos distintos
- `deleteCustomer()` ya es una capacidad excepcional y bloquea clientes con
  pedidos operativos, rol compartido o uso como destino canonico de fusion
- `orders` ya conserva `customerId`, `customerConflictId`, `crmStage` y
  `commercialTrace` como parte de su propio dominio

## Problema de negocio que resuelve este slice

Huele Huele necesita fijar una narrativa canonica para el dominio real de
clientes: donde vive el perfil vivo, como se resuelven duplicados nacidos de
pedidos, cuando aplica una fusion operativa y donde termina el ownership de
`customers` para no absorber el seguimiento comercial que hoy sigue viviendo
en `orders`.

## Flujo funcional consolidado

### 1. Maestro de clientes y perfil canonico

1. `ventas` abre `/crm`.
2. Crea o edita un cliente.
3. El sistema persiste perfil, estado, direcciones y datos base.
4. El detalle del cliente muestra pedidos recientes como contexto.
5. El perfil canonico queda en `customers`, no en `orders`.

### 2. Resolucion de conflictos de identidad

1. Un pedido genera una ambiguedad de identidad.
2. El sistema abre un conflicto con candidatos.
3. `ventas` revisa senales y selecciona `assign_existing`, `merge` o `ignore`.
4. La resolucion actualiza la referencia operativa necesaria sin reescribir
   arbitrariamente snapshots historicos.
5. El conflicto queda trazado con estado, resolucion y notas.

### 3. Fusion operativa de clientes

1. `ventas` selecciona un cliente fuente y un cliente destino.
2. El sistema valida que no tengan documentos canonicos distintos.
3. El destino permanece activo como perfil canonico.
4. La fuente queda marcada como fusionada.
5. `orders` regulariza la referencia canonica donde el runtime lo requiere,
   preservando la historia transaccional.

## Requerimientos funcionales

### RF-01. `customers` es el agregado principal

- la unidad operativa principal del slice es el cliente canonico
- el perfil vivo, estado y direcciones viven en `customers`
- `orders` no se promueve a owner del perfil

### RF-02. `/crm` es la superficie visible del slice

- `/crm` es el workbench canonico para operar clientes
- la pantalla concentra metricas, clientes, conflictos, detalle y merge
- el slice no abre una segunda superficie paralela para el mismo ownership

### RF-03. Prioridad canonica de identidad

- `documento` es la senal principal de identidad
- `email` y `telefono` son senales secundarias
- `nombre + direccion` solo opera como senal debil auxiliar
- el slice no debe fusionar clientes por coincidencias blandas sin guardrails

### RF-04. Conflictos y acciones operativas

- los conflictos usan `open`, `resolved`, `ignored` y `merged`
- la resolucion admite `assign_existing`, `merge` e `ignore`
- la resolucion deja trazabilidad con actor y notas
- un conflicto resuelto no debe abrirse de nuevo como si siguiera pendiente

### RF-05. Merge con destino canonico

- la fusion deja un cliente destino activo
- la fuente queda marcada como fusionada
- no se borra historia operativa
- no se puede fusionar si ambos clientes ya tienen documentos canonicos
  distintos

### RF-06. Clientes sinteticos o regularizados

- el runtime puede materializar clientes desde pedidos
- esos clientes forman parte valida del dominio actual
- el slice no exige que todo cliente nazca como cuenta limpia preexistente

### RF-07. Lectura de pedidos recientes como contexto

- el detalle del cliente incluye pedidos recientes
- esa lectura da contexto operativo
- esa lectura no transfiere ownership de `orders` hacia `customers`

### RF-08. `deleteCustomer` como capacidad excepcional

- el runtime ya expone eliminacion de clientes
- el borrado no es flujo principal del slice
- el sistema debe bloquear borrados incompatibles con pedidos, roles
  compartidos o uso como destino canonico

### RF-09. Frontera con `orders`

- `orders` conserva `customerId`, `customerConflictId`, `crmStage` y
  `commercialTrace`
- `customers` corrige identidad viva sin absorber seguimiento comercial
- el slice no debe venderse como CRM amplio o modulo de pipeline comercial

## Requerimientos no funcionales

- trazabilidad de actor, resolucion y notas en conflictos y merges
- consistencia entre perfil canonico y referencias operativas
- preservacion de historia transaccional de pedidos
- semantica clara entre cliente activo, cliente fusionado y conflicto abierto
- restricciones explicitas para borrado operativo

## Reglas canonicas del slice

- `customers` es el agregado principal del slice
- `/crm` es la superficie visible del slice
- `ventas` es owner operativo principal
- la prioridad de identidad es `documento`, luego `email/telefono`, luego
  `nombre + direccion`
- los conflictos usan `open`, `resolved`, `ignored` y `merged`
- la resolucion operativa usa `assign_existing`, `merge` e `ignore`
- no se puede fusionar si ambos clientes ya tienen documentos canonicos
  distintos
- clientes sinteticos o regularizados desde pedidos forman parte valida del
  runtime actual
- `orders` conserva snapshots historicos, `customerId`, `customerConflictId`,
  `crmStage` y `commercialTrace`
