# Fase 2 - UX/UI Notifications Outbox Y Expansion De Canales

## Objetivo

Formalizar la UX operativa vigente de `/notificaciones` como workbench del
outbox saliente del brownfield, sin convertir esta superficie en inbox,
consola de remediacion, scheduler real ni centro conversacional por cliente.

## Fuentes de runtime

- `apps/admin/app/notificaciones/page.tsx`
- `apps/admin/components/notifications-workspace.tsx`
- `apps/admin/lib/api.ts`
- `apps/api/src/modules/notifications/notifications.controller.ts`
- `apps/api/src/modules/notifications/notifications.service.ts`
- `docs/flows/campaigns-and-notifications.md`

## Superficie principal

### `/notificaciones`

- es la superficie operativa principal del slice
- abre con `SectionHeader` de `Notificaciones`
- la shell del modulo usa `AdminAuthGate` con descripcion
  `Mensajes internos y logs de envío.`
- expone metric cards para:
  - total de notificaciones
  - pendientes
  - enviadas
  - total de logs
- no expone hoy metricas separadas de `delivered` o `failed`
- resuelve `loading` y `error` con mensajes inline simples al pie de la
  pantalla

## Componentes principales

### Formulario `Nueva notificación`

- permite alta manual dentro del mismo workbench
- captura:
  - `channel`
  - `audience`
  - `subject`
  - `body`
  - `source`
  - `scheduledAt`
- el canal arranca en `email`
- `audience`, `subject`, `body` y `source` salen prellenados con valores
  demo-operativos
- `scheduledAt` usa `datetime-local`
- la CTA unica es `Crear notificación`
- al guardar:
  - el formulario entra en `Guardando...`
  - se registra la unidad en cola
  - `subject`, `body` y `scheduledAt` se resetean
- la UI manual actual no captura `relatedType` ni `relatedId`

### Tabla `Notificaciones`

- es la lectura principal del outbox materializado
- usa `AdminDataTable` con paginacion basica
- columnas visibles:
  - `Canal`
  - `Audiencia`
  - `Asunto`
  - `Estado`
  - `Origen`
  - `Programada`
  - `Enviada`
  - `Actualizada`
- `Estado` se muestra con `StatusBadge`
- `Programada` renderiza `scheduledAt`
- `Enviada` renderiza `sentAt`
- la tabla no expone hoy:
  - `body`
  - `relatedType`
  - `relatedId`
  - provider
  - botones de retry o cancelacion

### Tabla `Bitácora`

- es la lectura secundaria del timeline tecnico
- usa `AdminDataTable` con paginacion basica
- columnas visibles:
  - `Evento`
  - `Fuente`
  - `Sujeto`
  - `Detalle`
  - `Fecha`
- hoy resume eventos de pedidos, loyalty, campañas y acciones manuales
- no expone drill-down tecnico por provider, payload, backoff o requeue
  aunque el canon los reserve como evidencia posible de `NotificationLog`

## Estados visibles y semantica actual

- `pending` se presenta como `Pendiente`
- `sent` se presenta como `Enviada`
- `delivered` se presenta como `Entregada`
- `failed` se presenta como `Fallida`
- `email`, `sms`, `whatsapp` e `internal` son seleccionables desde la UI
- `scheduledAt` se presenta como metadata visible y no como scheduler probado

## Contrato UX del slice

- `NotificationsWorkspace` sigue siendo la superficie principal visible
- `/notificaciones` combina alta manual, lectura del outbox y lectura de logs
  en una sola pagina
- la tabla del outbox representa unidades individuales por `audience` y canal
- la bitacora representa evidencia tecnica u operativa acumulada, no un chat
- la UI no promete delivery confirmado para todos los canales
- la UI no presenta hoy filtros dedicados por `channel`, `source`, `status` o
  relacion de negocio; esas lecturas quedan implicitas en columnas y tablas,
  no como widgets explicitos
- la UI no presenta scheduler real, inbox, reply, resend, retry manual ni
  edicion post-creacion

## Regla UX critica

- `/notificaciones` debe sentirse como workbench de outbox saliente
- la lectura del mensaje y de su estado debe ser operativa, no conversacional
- el timeline tecnico debe sentirse como evidencia de delivery, no como
  experiencia de soporte humano

## Criterio de cierre

- `/notificaciones` queda documentado como superficie principal del slice
- el formulario manual, la tabla del outbox y la tabla de logs quedan
  anclados al runtime visible
- la ausencia de inbox, remediacion manual y filtros explicitamente
  implementados queda documentada sin sobreprometer capacidades nuevas
