# Fase 1 - Campaigns Marketing Automation

## Objetivo

Homologar el modulo `marketing` vigente de Huele Huele como bounded context de
campanas operativo, sin convertirlo en un journey engine ni mezclarlo con CRM
ampliado.

## Alcance del slice

### Dentro de alcance

- `campaigns` como agregado operativo principal
- `segments` como catalogo read-only usado por campanas
- `templates` como catalogo read-only usado por campanas
- canales `email`, `sms` y `whatsapp`
- scheduling basico por `scheduledAt`
- `status` y `runStatus` de campana
- snapshot operativo congelado al crear:
  `segmentName`, `templateName`, `bodyPreview` y `recipients`
- `events` e historial operativo de campanas
- frontera `marketing -> notifications -> worker`

### Fuera de alcance

- journeys
- triggers multi-step
- authoring completo de `segments`
- authoring completo de `templates`
- A/B testing de campanas
- analytics avanzados
- CRM ampliado
- cambiar el ownership de entrega hacia `marketing`

## Estado actual que se conserva

- `marketing` ya persiste `segments`, `templates`, `campaigns` y `events` en
  su snapshot operativo
- la API ya expone lectura de campanas, segmentos, plantillas y eventos bajo
  `/admin/campaigns`
- la creacion de campanas ya exige `name`, `goal`, `segmentId`,
  `templateId` y `channel`
- el runtime actual valida existencia de `segmentId` y `templateId`, mas
  compatibilidad entre `template.channel` y `campaign.channel`
- si `scheduledAt` viene vacio, la campana nace `running/running`
- si `scheduledAt` viene informado, la campana nace `scheduled/queued`
- al crear la campana se congelan `segmentName`, `templateName`,
  `bodyPreview` y `recipients`
- el runtime actual no aplica un hard gate adicional por estado de catalogo;
  la decision minima real es `name`, `goal`, existencia de IDs y
  compatibilidad de canal
- `/marketing` ya permite seleccionar segmento, plantilla, canal, objetivo y
  programacion
- `marketing` registra auditoria y eventos operativos, pero no ejecuta el
  dispatch real del mensaje
- `notifications` conserva la cola y el estado tecnico de entrega; `worker`
  procesa el dispatch real por canal soportado

## Problema de negocio que resuelve este slice

Huele Huele necesita fijar una narrativa canonica para el dominio real de
campanas: quien crea y programa una campana, que dependencias lee del catalogo
de segmentos y plantillas, como se congela el snapshot de negocio al momento
de crearla y donde termina la orquestacion de marketing para dejar el dispatch
real en `notifications/worker`.

## Actores y roles implicados

| Actor / rol | Responsabilidad en este slice |
| --- | --- |
| marketing | owner operativo del workbench, crea campanas, elige catalogos y define objetivo, canal y `scheduledAt` |
| admin | soporte transversal y override operativo del modulo |
| super_admin | acceso total para recuperacion y soporte avanzado |
| campaigns | agregado principal del slice y fuente de estado operativo de campanas |
| segments | catalogo read-only de audiencia disponible |
| templates | catalogo read-only de contenido reutilizable por canal |
| notifications | cola, logs y estado tecnico de entrega |
| worker | procesamiento asincrono y dispatch real por canal soportado |

Roles habilitados segun matriz vigente:

- `marketing` como owner principal con `marketing.read`, `marketing.write` y
  `marketing.execute`
- `admin` y `super_admin` con soporte transversal sobre campanas y segmentos

## Flujo funcional consolidado

### 1. Creacion y programacion de campanas

1. `marketing` abre el workbench de campanas.
2. Define nombre, objetivo, segmento, plantilla y canal.
3. Opcionalmente informa `scheduledAt`.
4. `campaigns` crea la campana con estado inicial coherente.
5. La campana queda inmediatamente `running/running` o `scheduled/queued`
   segun exista programacion.

### 2. Seleccion read-only de segmentos y plantillas

1. `marketing` consulta el catalogo de segmentos disponibles.
2. `marketing` consulta el catalogo de plantillas disponibles.
3. El sistema exige que los IDs seleccionados existan.
4. El sistema exige que `template.channel` coincida con el canal elegido para
   la campana.
5. El slice conserva estos catalogos como dependencias read-only `as-is`.

### 3. Frontera de dispatch y entrega

1. `marketing` registra la campana y sus eventos operativos.
2. El flujo visible actual termina en `marketing`; el cruce hacia
   `notifications` queda como boundary canonico para otra integracion o flujo
   explicito.
3. Cuando esa frontera se cruza por otro flujo, `notifications` encola,
   registra y actualiza el estado tecnico de la notificacion.
4. `worker` procesa el dispatch real por el canal soportado para jobs ya
   encolados.
5. El resultado tecnico de envio no pertenece al agregado `campaigns`.

## Requerimientos funcionales

### RF-01. `campaigns` es el agregado principal

- la unidad operativa principal del slice es la campana
- el estado de campana vive en `status`, `runStatus`, metadatos y snapshot
- `segments` y `templates` no se promueven a agregados authorables en este
  corte

### RF-02. Scheduling basico por `scheduledAt`

- `scheduledAt` es el unico mecanismo canonico de programacion del slice
- sin `scheduledAt` la campana nace `running/running`
- con `scheduledAt` la campana nace `scheduled/queued`

### RF-03. Snapshot congelado al crear la campana

- la campana debe conservar `segmentId` y `templateId`
- tambien debe congelar `segmentName`, `templateName`, `bodyPreview` y
  `recipients`
- cambios posteriores en segmentos o plantillas no deben reescribir
  retroactivamente el snapshot de la campana

### RF-04. Catalogos read-only para segmentos y plantillas

- `segments` y `templates` se consumen como catalogos read-only `as-is`
- el slice canonico no abre editor, versionado ni lifecycle propio para ellos
- la seleccion operativa ocurre desde el workbench de `marketing`

### RF-05. Hard gates minimos reales del runtime

- el runtime actual exige `name`
- el runtime actual exige `goal`
- el runtime actual exige existencia de `segmentId`
- el runtime actual exige existencia de `templateId`
- el runtime actual exige compatibilidad entre `template.channel` y
  `campaign.channel`
- el runtime actual no eleva estados de catalogo a hard gate fuerte del slice

### RF-06. Eventos e historial operativo

- `marketing` registra eventos del dominio para campanas y actividad comercial
- la campana conserva historial de estado con actor, nota y fecha
- la trazabilidad operativa debe existir aun si la entrega real ocurre fuera
  del modulo

### RF-07. Ownership operativo en `marketing`

- `marketing` decide el objetivo comercial, audiencia elegida, plantilla,
  canal y programacion
- `marketing` no es duenio del envio fisico por proveedor
- el owner funcional del slice sigue siendo `marketing`, no `notifications`

### RF-08. Dispatch desacoplado

- desde una campana ya registrada, `notifications` recibe y registra la
  intencion downstream de notificacion
- `worker` procesa la cola y marca resultado tecnico por canal soportado
- `campaigns` no debe saltarse esta frontera para entregar directo

### RF-09. Sin journeys ni CRM ampliado

- el slice no modela journeys
- el slice no modela triggers multi-step
- el slice no se extiende a CRM ampliado ni scoring comercial avanzado

## Requerimientos no funcionales

- trazabilidad de actor, IDs referenciados y `scheduledAt`
- consistencia de canal entre campana y plantilla
- separacion explicita entre orquestacion de marketing y dispatch tecnico
- persistencia snapshot-backed sin reescritura retroactiva de campanas ya
  creadas
- semantica consistente entre admin, API y worker para estados de campana y
  entrega

## Regla critica

- `marketing` crea y orquesta la campana
- `campaigns` es el agregado principal del slice
- sin `scheduledAt` la campana nace `running/running`
- con `scheduledAt` la campana nace `scheduled/queued`
- la campana congela snapshot operativo al crearse
- `notifications/worker` resuelven la entrega real del mensaje

## Reglas canonicas del slice

- `campaigns` es el agregado principal del slice
- `segments` y `templates` entran como catalogos read-only `as-is`
- `scheduledAt` define si la campana nace en ejecucion inmediata o programada
- la campana congela snapshot de segmento y plantilla al crearla
- `marketing` orquesta; `notifications/worker` despachan
- journeys, automation multi-step y CRM ampliado quedan fuera

El detalle operativo queda consolidado en

## Riesgos y tensiones del estado actual

- asumir elegibilidad fuerte por estado de catalogo cuando el runtime hoy no la
  aplica
- reescribir la semantica de campana despues de cambios posteriores en
  segmentos o plantillas
- confundir el workbench de campanas con un journey builder o con CRM ampliado
- colapsar la frontera entre `marketing` y `notifications/worker`
- sobreprometer dispatch productivo homogéneo para todos los canales
