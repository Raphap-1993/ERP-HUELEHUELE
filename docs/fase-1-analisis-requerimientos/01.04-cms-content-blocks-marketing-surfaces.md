# Fase 1 - CMS Content Blocks Marketing Surfaces

## Objetivo

Homologar el CMS editorial vigente de Huele Huele como dominio operativo
canonico, sin convertirlo en un page builder libre ni mezclarlo con campaigns,
segments o CRM ampliado.

## Alcance del slice

### Dentro de alcance

- `site settings`
- `hero copy`
- `navigation`
- media publica asociada al CMS
- `banners`, `faqs` y `testimonials`
- `pages` conocidas
- `blocks` tipados por ruta conocida
- `seoMeta` por ruta conocida
- fallback seguro a defaults editoriales cuando el snapshot CMS falle o llegue
  incompleto

### Fuera de alcance

- campaigns
- segments
- templates
- CRM ampliado
- page builder libre
- rutas publicas arbitrarias creadas desde admin
- bloques genericos sin contrato editorial conocido
- approval workflow multinivel
- art direction premium del storefront

## Estado actual que se conserva

- `/admin/cms` ya opera paginas, bloques, banners, FAQs y testimonios desde el
  runtime vivo
- el snapshot CMS ya persiste `siteSetting`, `heroCopy`, `webNavigation`,
  `banners`, `faqs`, `pages`, `testimonials` y `seoMeta`
- `site settings` ya concentra branding y media publica como
  `headerLogoUrl`, `adminSidebarLogoUrl`, `heroProductImageUrl`,
  `loadingImageUrl` y `faviconUrl`
- `banners`, `faqs` y `testimonials` ya usan semantica corta
  `active/inactive`
- los `page blocks` del runtime tambien ya exponen `active/inactive` como
  bandera de render dentro de una pagina conocida
- `pages` ya usan `draft`, `published` y `archived`
- el snapshot ya modela rutas conocidas con SEO operativo:
  `home`, `catalogo`, `mayoristas`, `trabaja-con-nosotros`, `cuenta` y
  `checkout`
- el storefront ya consume hero, FAQ, testimonios y media publica desde CMS y
  cae a fallback seguro cuando el snapshot no responde o llega incompleto

## Contrato entre colecciones y bloques por ruta

- `banners`, `faqs` y `testimonials` viven como colecciones editoriales
  compartidas en el snapshot CMS y no como paginas separadas
- los bloques de pagina por ruta conocida no crean una segunda coleccion: son
  contratos de ubicacion y render sobre una ruta conocida
- el bloque `promo-banner` en `home` representa el slot editorial que consume
  `banners` `active`
- el bloque `faq` en `home` representa el slot editorial que consume `faqs`
  `active`
- en el brownfield actual no existe un bloque canonico `testimonial` dentro de
  `pages.blocks`; las superficies aprobadas consumen `testimonials` `active`
  desde la coleccion top-level del snapshot
- si una ruta no declara el bloque consumidor correspondiente, la coleccion
  compartida no debe asumirse como render obligatoria para esa pagina

## Problema de negocio que resuelve este slice

Huele Huele necesita fijar una narrativa canonica para su CMS editorial real:
quien lo opera, que contenido gobierna, que rutas publicas reconoce, como se
publica SEO por ruta y como se protege la web publica cuando el snapshot CMS no
es valido. El objetivo es documentar el dominio tal como existe hoy, no abrir
otro producto de marketing.

## Actores y roles implicados

| Actor / rol | Responsabilidad en este slice |
| --- | --- |
| marketing | dueno operativo principal del CMS, edita contenido, publica paginas conocidas y gobierna SEO |
| cms | persiste snapshot editorial, estructura de paginas, bloques y estados |
| media | sube y reemplaza assets publicos del CMS manteniendo URLs validas |
| web/storefront | consume snapshot valido y aplica fallback seguro si falta contenido |
| admin | audita, corrige excepciones y conserva override operativo |
| super_admin | mantiene control total para soporte y recuperacion |

Roles habilitados segun matriz vigente:

- `marketing` como owner principal con `cms.read`, `cms.write` y `cms.publish`
- `admin` y `super_admin` con capacidad de soporte y override

## Modulos y superficies implicadas

- backoffice `/admin/cms`
- `cms`
- `media`
- `web/storefront`
- `module_snapshots` como persistencia del snapshot editorial
- auditoria de acciones administrativas

## Rutas conocidas del slice

Las unicas rutas publicas reconocidas por este slice son:

- `home`
- `catalogo`
- `mayoristas`
- `trabaja-con-nosotros`
- `cuenta`
- `checkout`

No se abre creacion de slugs arbitrarios como capacidad canonica de negocio.

## Flujo funcional consolidado

### 1. Configuracion global y media publica

1. `marketing` edita `site settings`, `hero copy` o `navigation`.
2. `marketing` actualiza logo, favicon, hero image u otros assets publicos del
   CMS.
3. `cms` persiste el snapshot global actualizado.
4. `web/storefront` consume la configuracion valida mas reciente.

### 2. Publicacion de paginas y bloques

1. `marketing` opera una ruta conocida.
2. Asigna o reordena bloques tipados compatibles con esa ruta.
3. La pagina queda `draft`, `published` o `archived`.
4. `cms` persiste estructura editorial y `seoMeta` por ruta.

### 3. Consumo publico con SEO y fallback

1. `web/storefront` intenta cargar el snapshot CMS.
2. Si el snapshot es valido, consume `seoMeta`, contenido activo y paginas
   publicables.
3. Si el snapshot falla o llega incompleto, la superficie publica usa defaults
   seguros.
4. La ruta sigue renderizando sin romper la operacion.

## Requerimientos funcionales

### RF-01. Singletons globales del sitio

- `site settings`, `hero copy` y `navigation` son singleton globales
- no se administran como paginas separadas ni como bloques libres
- su cambio afecta la lectura editorial del sitio y no requiere campaign

### RF-02. Media publica del CMS

- el CMS gobierna media publica de branding y lectura editorial
- las URLs publicas de logo, sidebar admin, hero, loading y favicon son parte
  del snapshot CMS
- `media` resuelve el upload tecnico; `marketing` decide el contenido publicado

### RF-03. Assets editoriales cortos

- `banners`, `faqs` y `testimonials` son assets editoriales cortos
- usan `active/inactive`
- el storefront solo debe exponer items `active`
- `promo-banner` y `faq` son bloques consumidores de esas colecciones y no
  copias paralelas de contenido

### RF-04. Paginas conocidas y ciclo editorial

- las `pages` usan `draft`, `published` y `archived`
- solo se reconocen las rutas conocidas del slice
- `archived` no debe exponerse en vista publica

### RF-05. Bloques tipados por ruta conocida

- cada ruta conocida admite solo un conjunto acotado de bloques tipados
- el CMS no abre composicion libre ni bloques arbitrarios
- los `page blocks` usan `active/inactive` como bandera de render dentro de la
  pagina, sin reemplazar el estado editorial de la `page`
- `promo-banner` y `faq` funcionan como consumidores de colecciones compartidas
  del snapshot; `testimonials` se consume hoy desde la coleccion top-level y no
  desde un bloque canonico de pagina
- la relacion bloque-ruta queda como regla funcional del dominio aunque la
  validacion tecnica evolucione despues

### RF-06. SEO operativo por ruta

- cada ruta conocida puede definir `title`, `description`, `keywords`,
  `canonicalPath` y `robots`
- `cuenta` y `checkout` pueden operar con `noindex,nofollow`
- el SEO pertenece a la pagina conocida y no a campaigns

### RF-07. Publicacion editorial directa

- `marketing` es el owner operativo principal del slice
- en este corte no existe aprobacion editorial multinivel obligatoria
- `admin` y `super_admin` conservan override para excepciones y soporte

### RF-08. Fallback seguro del storefront

- si el snapshot CMS no responde, falla o llega incompleto, la superficie
  publica debe seguir renderizando
- el fallback usa defaults seguros ya curados para hero, FAQ, testimonios,
  banners y branding publico cuando corresponda
- el fallback no debe exponer contenido archivado ni inventar rutas nuevas

### RF-09. Frontera con campaigns y CRM

- el CMS editorial no gobierna campanas, segmentos ni automatizaciones
- este slice no modela audiencias, templates ni corridas de campaign
- `marketing` opera aqui contenido editorial y SEO, no CRM ampliado

## Requerimientos no funcionales

- persistencia snapshot-backed sin romper el patron brownfield actual
- trazabilidad de cambios editoriales y de media
- tolerancia a fallas en lectura publica mediante fallback seguro
- semantica consistente entre admin, API y storefront para estados y rutas
- no degradar rutas publicas conocidas por snapshot invalido o incompleto

## Regla critica

- el CMS administra contenido editorial real y SEO operativo por ruta conocida
- si el snapshot falla o llega incompleto, storefront aplica fallback seguro
- este slice no se convierte en campaigns, CRM ni page builder libre

## Reglas canonicas del slice

- `marketing` es el dueno operativo principal del CMS
- `site settings`, `hero copy` y `navigation` son singleton globales
- `banners`, `faqs` y `testimonials` usan `active/inactive`
- `pages` usan `draft/published/archived`
- solo existen rutas conocidas en este slice
- los bloques permitidos dependen de la ruta conocida
- `checkout` y `cuenta` pueden operar con `noindex,nofollow`
- el storefront aplica fallback seguro si falla el snapshot CMS
- el CMS editorial no gobierna campaigns ni CRM ampliado

El detalle operativo queda consolidado en
[reglas/cms-y-superficies-editoriales.md](./reglas/cms-y-superficies-editoriales.md).

## Riesgos y tensiones del estado actual

- confundir CMS editorial con page builder libre
- mezclar SEO operativo del sitio con campanas y segmentacion
- permitir slugs o bloques arbitrarios que no existen en runtime
- romper la web publica por snapshot incompleto o media invalida
- asumir que el CMS controla la logica transaccional de `checkout` o `cuenta`
- perder `noindex,nofollow` en rutas sensibles

## Criterios de aceptacion del slice documental

- existe un documento rector de Fase 1 para el CMS editorial
- existen casos de uso separados para configuracion global, publicacion y
  consumo publico con fallback
- ownership, estados, rutas conocidas y SEO por ruta quedan explicitos
- campaigns, CRM y page builder libre quedan fuera de alcance sin ambiguedad
