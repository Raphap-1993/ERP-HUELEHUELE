# Fase 2 - UX/UI

## Objetivo

Consolidar la UX canonica del slice inicial de checkout y pagos sobre el estado publico vigente del storefront, sin introducir una pasarela online visible y sin mover la responsabilidad operativa fuera de backoffice.

## Principio rector

La experiencia publica debe sentirse como un checkout claro y directo de tres pasos, pero el cierre comercial real del slice sigue dependiendo de pago manual con comprobante y confirmacion operativa humana.

## Superficie cubierta

- ruta publica `/checkout`
- wizard de tres pasos
- rail lateral de resumen
- modal de comprobante
- implicancias operativas visibles para cliente y para backoffice

## Lo que la UX debe mantener intacto

- `quote` sigue viniendo de backend
- la creacion del pedido y del pago sigue gobernada por API
- la UI publica no expone cupones, codigos de vendedor ni descuento visible
- la experiencia visible hoy cierra con pago manual
- `Pagos` sigue resolviendo comprobantes y `Pedidos > Operacion` sigue concentrando la trazabilidad comercial

## Arquitectura UX del checkout

### Paso 1. Pedido

- el checkout abre directo al flujo, sin bloque editorial previo
- el shell usa una sola intencion principal: revisar y confirmar el pedido
- el selector de referencias se mantiene ligero y enfocado en las tres referencias activas del MVP
- el resumen lateral prioriza subtotal, envio, total y modo de entrega

### Paso 2. Datos y envio

- la primera tarea visible es identidad documental
- la secuencia funcional es: documento, entrega, ubicacion, contacto
- el checkout intenta precargar informacion del cliente cuando existe coincidencia canonica
- si el documento es `DNI`, el nombre autocompletado debe confirmarse visualmente antes de avanzar
- el ubigeo depende del modo de entrega elegido

### Paso 3. Pago y confirmacion

- el paso final refuerza que el pago visible hoy es manual por billetera virtual
- el numero y el titular de la billetera deben verse antes del modal
- el CTA principal conduce a pagar y luego subir comprobante
- la evidencia se carga en un modal, no en una ruta aparte
- la UI no promete confirmacion inmediata del pedido solo por subir el comprobante

## Decision UX canonica del slice

### Pago manual visible

El paso final del wizard se diseña alrededor de un camino operativo real: el cliente paga fuera de la plataforma, envia el comprobante y espera validacion humana.

Implicancias:

- la interfaz debe usar copy comercial claro y no lenguaje tecnico de conciliacion
- el cliente necesita entender que el comprobante forma parte del cierre del pedido
- la carga de evidencia es obligatoria dentro del estado vigente

### Superficie online futura oculta

La documentacion reconoce que existe una frontera de gateway online futura, pero la UX actual no la activa.

Implicancias:

- no se muestra selector de pasarela online
- no se muestra dualidad `manual vs online`
- no se redisenan componentes para un provider que aun no gobierna la operacion real

## Shell y composicion visual

- contenedor editorial ancho en desktop para evitar columna demasiado comprimida
- barra de progreso visible
- cabeceras de paso con orientacion breve y accion clara
- footer global oculto en la ruta para priorizar una sola pantalla operativa
- fondo continuo y limpio para evitar ruido visual
- resumen lateral persistente en desktop y compacto cuando el pedido crece

## Interacciones clave

### Identidad

- documento obligatorio para todo checkout
- lookup previo por documento antes de depender de `ApiPeru`
- nombre visible con jerarquia suficiente en la revision final

### Entrega

- selector de envio como dos cards: `Delivery Lima/Callao` y `Shalom provincia`
- restricciones de ubigeo visibles desde el copy, no solo desde el error
- sucursal de recojo obligatoria cuando aplica `Shalom`

### Pago manual

- CTA principal `Pagar ahora`
- accion de copiado rapido del numero de billetera
- modal alineado al lenguaje visual del checkout
- accion secundaria para seguimiento por WhatsApp una vez enviado el pedido

## Reglas de contenido y copy

- el cliente no ve estados como `pending_payment`, `payment_under_review` o `confirmed`
- el copy habla de `verificacion`, `comprobante` y `confirmacion del pedido`, no de jobs, colas o conciliacion
- la UI no mezcla instrucciones de `Pagos` con el discurso publico del checkout

## Relacion con backoffice

### `Pagos`

- revisa comprobantes manuales
- necesita ver contexto suficiente del pedido, pero no reemplaza el detalle comercial del mismo

### `Pedidos > Operacion`

- concentra la lectura canonica del pedido
- muestra ruta operativa activa, referencia, notas y fechas del cierre comercial
- es la superficie prevista para una futura conciliacion controlada de pagos online mientras no exista webhook confiable

## Estados y feedback esperados en UX

- `cotizando`: feedback breve sin tecnicismos
- `datos incompletos`: error por seccion, no banner generico permanente
- `comprobante invalido`: mensaje inmediato y accionable
- `envio recibido`: confirmacion de recepcion del pedido y del comprobante
- `revision operativa`: se comunica como verificacion, no como estado interno del dominio

## Riesgos abiertos que la UX debe reconocer

- el runtime actual crea el pedido al confirmar el modal con comprobante; la documentacion de UX lo reconoce y no lo maquilla como reserva temprana
- una falla tardia de disponibilidad sigue siendo posible mientras no cambie el flujo tecnico
- la UX debe seguir evitando errores crudos o detalles internos expuestos al cliente

## Criterios de aceptacion de Fase 2

- la UX documentada mantiene el wizard de tres pasos
- el pago manual es la unica via visible del checkout actual
- la superficie online futura queda explicitamente oculta
- el backoffice queda dividido entre `Pagos` y `Pedidos > Operacion`
- la experiencia publica y la operativa documentada no se contradicen entre si
