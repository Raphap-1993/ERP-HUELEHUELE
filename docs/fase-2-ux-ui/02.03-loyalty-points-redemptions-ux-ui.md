# Fase 2 - UX/UI Loyalty Points Redemptions

## Objetivo

Formalizar la UX del programa de puntos vigente sin convertir `/cuenta` en
autoservicio de canjes ni sacar a `marketing` de la operacion del modulo.

## Fuentes de runtime

- `apps/web/components/account-workspace.tsx`
- `apps/admin/components/loyalty-workspace.tsx`
- `apps/admin/app/loyalty/page.tsx`
- `docs/flows/loyalty-flow.md`

## Superficies

### `/cuenta`

- muestra saldo disponible, pendiente y canjeado
- muestra el estado reciente del programa
- debe sentirse como resumen de fidelizacion, no como mesa operativa
- no debe sugerir que el cliente puede crear canjes desde esa pantalla

### `/admin/loyalty`

- es la superficie operativa principal del programa
- aqui viven reglas, ajustes, movimientos, cuentas y resolucion de canjes
- debe sentirse como workbench operativo de `marketing`, no como un simple
  reporte historico

## Contrato UX del slice

- el cliente ve visibilidad del programa, no autoservicio de canje
- `marketing` ve control operativo sobre earn, ajustes y canjes
- el programa debe leerse como contabilidad simple de puntos, no como motor
  promocional complejo
- el estado `pending` del canje debe comunicar reserva, no aplicacion final

## Regla UX critica

- `/cuenta` no inicia canjes
- el canje `pending` ya implica puntos retenidos
- `applied` y `cancelled` deben leerse como decisiones operativas del admin
- el cliente no debe interpretar un canje pendiente como beneficio ya ganado

## Criterio de cierre

- las superficies loyalty quedan nombradas y delimitadas
- el contrato UX no contradice el runtime vigente
- Fase 3 puede heredar ownership y fronteras sin reabrir el diseno del
  producto
