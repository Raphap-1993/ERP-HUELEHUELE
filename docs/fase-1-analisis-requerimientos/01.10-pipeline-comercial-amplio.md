## Flujo funcional consolidado

### 1. Apertura y etapado del caso comercial

1. El `customer_relationship_case` ya existe o se acaba de abrir.
2. `ventas` inicializa `pipelineStage` en `new` o en otra etapa si ya hay
   contexto comercial suficiente.
3. El operador define `priority` y `commercialChannel`.
4. El caso conserva `commercialOwner`, `assignee`, `nextStep` y
   `followUpAt`.
5. Todo cambio posterior de etapa queda trazado en el timeline.

### 2. Bandeja y priorizacion del pipeline comercial

1. El operador entra a la bandeja comercial dentro de `/crm`.
2. Filtra por `commercialOwner`, `assignee`, `pipelineStage`, `priority`,
   `commercialChannel` y `status`.
3. Revisa las vistas de pendientes de hoy y vencidos usando `followUpAt`.
4. `lastPipelineActivityAt` permite ordenar la cola sin leer todo el
   timeline.
5. El operador decide el siguiente movimiento comercial del caso.

### 3. Cierre comercial, `won`, `lost` y reapertura

1. `ventas` decide cerrar el pipeline como `won` o `lost`.
2. Si marca `lost`, registra `lostReason`.
3. Si marca `won`, registra nota de cierre y evidencia o referencia.
4. El timeline guarda el cambio de etapa comercial.
5. Si el caso estaba `lost`, puede reabrirse comercialmente con
   trazabilidad sin crear un caso nuevo.

## Requerimientos funcionales

### RF-01. El pipeline vive sobre el mismo caso transversal

- `customer_relationship_case` sigue siendo el agregado principal del slice
- `011` no crea un agregado nuevo de oportunidad
- sigue existiendo un solo caso por cliente canonico

### RF-02. `pipelineStage` es una dimension manual separada de `status`

- `pipelineStage` es manual por `ventas`
- `pipelineStage` y `status` son ejes distintos del mismo caso
- el sistema no cambia `pipelineStage` automaticamente por eventos tecnicos

### RF-03. Etapas canonicas del pipeline comercial

- el pipeline usa `new`
- el pipeline usa `contacted`
- el pipeline usa `engaged`
- el pipeline usa `nurturing`
- el pipeline usa `won`
- el pipeline usa `lost`

### RF-04. Trazabilidad obligatoria de cambios de etapa

- se permiten saltos manuales entre etapas
- todo cambio de `pipelineStage` deja una entrada obligatoria en el
  timeline
- la historia comercial no se pierde aunque el caso luego pase a
  `resolved` o `dormant`

### RF-05. Prioridad comercial manual

- el caso agrega `priority`
- `priority` usa `low`, `medium` y `high`
- la prioridad no se calcula automaticamente en este corte

### RF-06. Canal comercial principal del caso

- el caso agrega `commercialChannel`
- `commercialChannel` usa `storefront`, `vendor`, `wholesale`,
  `manual_outreach`, `reactivation` y `referral`
- el canal representa el origen principal del caso y no abre subpipelines
  separados

### RF-07. Cierre `lost` con motivo obligatorio

- pasar a `lost` exige `lostReason`
- `lostReason` usa `no_response`, `price`, `timing`, `competition`,
  `not_fit` y `other`
- `lost` cierra el pipeline comercial, pero no destruye el caso
  transversal

### RF-08. Cierre `won` con evidencia obligatoria

- `won` representa cierre comercial manual por `ventas`
- pasar a `won` exige nota de cierre
- pasar a `won` exige evidencia o referencia

### RF-09. `lastPipelineActivityAt` resume actividad comercial reciente

- `lastPipelineActivityAt` se actualiza con cambios de etapa
- `lastPipelineActivityAt` se actualiza con actividad manual relevante del
  caso
- `followUpAt` sigue siendo la unica fecha objetivo operativa del caso

### RF-10. Bandeja comercial operativa dentro de `/crm`

- la bandeja vive dentro del mismo modulo `/crm`
- la bandeja filtra por owner, assignee, etapa, prioridad, canal y status
- la bandeja ofrece vistas de pendientes de hoy y vencidos basadas en
  `followUpAt`

### RF-11. Guardrails entre `status` y `pipelineStage`

- `won` y `lost` son cierres comerciales, no cierres tecnicos del caso
- el sistema no cambia `status` automaticamente por cambiar
  `pipelineStage`
- el slice mantiene guardrails suaves sin acoplar ambos ejes como un solo
  workflow

## Requerimientos no funcionales

- trazabilidad completa de cambios de etapa, cierres y reaperturas
- consistencia entre `010`, el cliente canonico y la cola comercial
- claridad de ownership entre `ventas`, `marketing` y `customers`
- lectura rapida de prioridad, canal y ultima actividad sin abrir todo el
  timeline
- exclusion explicita de opportunities, scoring y automatizaciones
  comerciales
