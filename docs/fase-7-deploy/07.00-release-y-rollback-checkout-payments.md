# 07.00 Release y Rollback: Checkout y Payments

## Objetivo

Dejar el flujo minimo para liberar y revertir sin ambiguedad el slice `checkout publico + pago manual + frontera futura de gateway` sobre la topologia productiva vigente.

## Pre-Release Del Slice

Antes de desplegar:

- confirmar que el diff solo toca checkout, pagos manuales o su borde online
- confirmar si hay o no cambio de schema
- confirmar que la documentacion vigente del slice quedo actualizada
- identificar el commit o tag exacto a publicar

Gates locales:

```bash
npm run typecheck
npm run test:erp-sales
npm run build
```

## Despliegue Vigente

### 1. Snapshot y backup

- registrar el snapshot en Git
- si el corte toca schema o hay riesgo operacional alto, correr backup productivo antes del release
- no copiar ni restaurar base local sobre produccion

### 2. Release productiva

Comando canonico:

```bash
npm run deploy:release
```

Notas:

- el release vive en `releases/<timestamp>`
- `current` apunta a la release activa
- el entorno productivo se lee desde `/home/huelehuele/apps/huelegood.com/shared/.env.production`

### 3. PM2 y runtime

Procesos que deben quedar vivos:

- `huelegood-web`
- `huelegood-admin`
- `huelegood-api`
- `huelegood-worker`

Si el entorno cambio, la recarga debe hacerse con `--update-env`.

## Smoke Tecnico Obligatorio

Comando:

```bash
npm run deploy:smoke
```

Healthchecks minimos:

- `web /health`
- `admin /health`
- `api /health/liveness`
- `api /health/readiness`
- `api /health/operational`

## Smoke Funcional Del Slice

Ejecutar solo lo que el corte realmente toca, pero no cerrar release sin al menos un smoke funcional del frente afectado.

### Camino manual obligatorio

1. crear un pedido desde `/checkout`
2. confirmar que el pedido entra a revision
3. validar que la solicitud aparece en `/pagos`
4. aprobar o rechazar con actor y nota
5. confirmar en `/pedidos` la traza final

### Camino online solo si el corte toca la frontera gateway

1. generar o ubicar una orden `openpay` controlada
2. confirmar que `Pagos` no la trata como solicitud manual
3. resolverla desde `Pedidos > Operacion`
4. validar `commercialTrace.route = openpay_backoffice`

Regla:

- no exigir un smoke publico de `openpay` desde la UI mientras el checkout vigente siga expuesto en `manual`

## Rollback

### Rollback de codigo

Usar cuando el problema es de build, UI, runtime o logica sin necesidad de restaurar datos:

1. apuntar `current` a la release anterior
2. recargar PM2 con `--update-env`
3. correr `npm run deploy:smoke`
4. repetir el smoke funcional minimo del slice

### Contencion previa si cae el storefront

Si el problema deja inutilizable `/checkout`, se puede activar temporalmente:

- `WEB_MAINTENANCE_MODE`
- `WEB_MAINTENANCE_BYPASS_TOKEN` si se necesita validacion privada

Esto contiene el impacto mientras se hace rollback o fix-forward.

### Rollback de datos

Solo aplica con backup productivo y decision explicita.

No hacer:

- restore desde base local
- `prisma:seed` en produccion
- rollback de datos por intuicion sin revisar primero pedidos y pagos afectados en la ventana del incidente

## Matriz Minima De Decision

| Falla | Respuesta primaria |
| --- | --- |
| checkout publico roto despues del release | rollback de codigo o maintenance mode + fix-forward |
| cola manual visible pero sin confirmar | revisar `huelegood-api`, `huelegood-worker` y actor operativo antes de restaurar nada |
| pedido `openpay` confirmado por ruta equivocada | detener operacion sobre ese pedido, revisar auditoria y definir correccion controlada |
| error de entorno o secretos | corregir `.env.production` y recargar PM2 con `--update-env` |
| mutacion de datos incorrecta en lote | aislar ventana, revisar backup productivo y decidir rollback de datos por separado |

## Condicion De Cierre Del Release

El corte solo queda cerrado cuando:

- la release activa responde healthchecks
- PM2 corre contra la release correcta
- el camino manual del slice quedo probado
- si el corte toco la frontera online, la conciliacion controlada tambien quedo validada
